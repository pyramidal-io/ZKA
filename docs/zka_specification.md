## Abstract

Zero-Knowledge Agents (ZKA) is a protocol family enabling privacy-preserving interactions between autonomous agents. ZKA defines cryptographic primitives for private payments, verifiable coordination, and anonymous attestation.

This document specifies the **protocol layer**: circuit designs, proof formats, nullifier semantics, settlement interfaces, and the normative ZKA/ZKC integration that binds zero-knowledge compliance credentials to ZKA notes without linking identities. Implementation details are left to conforming systems.

ZKA targets **provable confidentiality**, not unconditional anonymity: a holder can prove specific properties (compliance predicates, balance thresholds, identity binding) to a chosen counterparty while revealing nothing else. The design treats compliance as an **interaction-boundary** concern, never a custody-boundary one — the architectural commitments that enforce this distinction are specified normatively in §1.6 (Freedom Safeguards as Protocol Invariants).

Public release changes are recorded in the root `CHANGELOG.md` of each public snapshot.

## 1. Overview

### 1.1 Design Goals

1. **Payment Privacy**: Transfer amounts and party identities are hidden from observers
2. **Double-Spend Prevention**: Nullifier-based consumption tracking prevents replay
3. **Verifiable Coordination**: Recursive proofs attest to multi-agent workflow execution
4. **Settlement Agnosticism**: Protocol works with any settlement layer (L2, L1, centralized)
5. **Selective Disclosure**: Viewing keys and predicate proofs enable audits without compromising privacy
6. **Provable Confidentiality**: A holder proves chosen properties to a chosen counterparty; non-compliance reduces counterparty access, never fund access
7. **Compliance Compatibility**: Normative integration with ZKC for user-controlled, pluralistic compliance
8. **Multi-Chain Deployment**: Aztec native, standalone EVM, and hybrid deployment models
9. **Freedom by Default**: The protocol invariants of §1.6 hold regardless of proving backend, settlement layer, or deployment context

### 1.4 Circuit Implementation

ZKA circuits are specified in **Noir** (ACIR IR) and proven using the **Barretenberg** backend (UltraHonk proving system) over the **BN254** scalar field. This enables:

- EVM-native Solidity verifiers generated by Barretenberg from an EVM-target verification key (`bb write_vk -t evm`, then `bb write_solidity_verifier -t evm`)
- Browser-based proving via NoirJS + Barretenberg WASM
- Aztec native deployment via `aztec.nr` private functions
- Pluggable backend: Barretenberg today, additional backends as Noir's ecosystem matures

The protocol invariants of §1.6 are implementation-independent and MUST hold for every conforming target.

### 1.6 Freedom Safeguards as Protocol Invariants

These six invariants are **normative**. A conforming implementation MUST satisfy all six; they are not optional features but the architectural commitments that distinguish privacy infrastructure from a compliance control mechanism. Safeguards 3 and 5 are core ZKA invariants; Safeguards 1, 2, and 4 are integration-level invariants binding any ZKC predicate or bundle used with ZKA (§5); Safeguard 6 is a verifier-accountability invariant that constrains the *counterparty* and is orthogonal to the operator-blindness of Safeguards 3 and 5.

**Safeguard 1 — Predicate Pluralism.** ZKA/ZKC MUST support multiple competing predicate providers simultaneously. No predicate provider may be hardcoded, privileged, or treated as canonical by the protocol, and the protocol MUST NOT include a mechanism for designating an "official" or "default" predicate set. Predicate providers are independent, permissionless services.

**Safeguard 2 — Minimal Disclosure by Default.** Predicate circuits MUST be designed for atomic, single-predicate proofs (e.g., "not sanctioned"), never bundled composites. Composite proofs MUST require explicit, separate consent per predicate. SDK and tooling defaults MUST generate minimal proofs; broader disclosure MUST require explicit additional configuration. Proof requests MUST be principal-readable, enumerating exactly what is proved.

**Safeguard 3 — No Revocability (core ZKA invariant).** ZKA note validity MUST depend solely on cryptographic properties — valid nullifier, valid commitment, valid Merkle path — never on an external authorization check. No admin, governance, emergency, or regulatory key may exist that can invalidate, freeze, redirect, or force-transfer a note. Smart-contract implementations MUST NOT include pausable, upgradeable, or admin-controlled functions that could affect note validity. The only consequence of non-compliance is counterparty refusal, never fund inaccessibility.

**Safeguard 4 — Open-Source Predicate Verification.** All predicate circuits MUST be open-source and publicly auditable, expressed in inspectable Noir code. If an agent cannot inspect the predicate it is asked to satisfy, the SDK MUST refuse to generate the proof by default. Predicate updates MUST be versioned, published, and subject to a public review period before activation.

**Safeguard 5 — Agent Exit Rights (core ZKA invariant).** Unshielding/withdrawal from ZKA to a base layer (e.g. Ethereum) MUST be unconditional — no compliance proof may gate exit. The protocol MUST distinguish *custody operations* (always permissionless) from *interaction operations* (may require compliance proofs for specific counterparties). This invariant is a protocol rule; it does not depend on any statute or pending legislation.

**Safeguard 6 — Verifier Accountability.** A verifier that requests a disclosure MUST authenticate the request under a stable verifier identity (an Authenticated Proof Request), and the holder MUST be able to retain a self-contained receipt of exactly what was demanded, for what declared purpose, and what was answered. A conforming SDK MUST refuse by default to answer an unauthenticated request, MUST bind declared purpose into the proof context, and MUST NOT require any operator or service to custody receipts. This safeguard governs the *request*; it makes no claim over the verifier's *decision*, which the protocol cannot reach (request accountability is reachable — no signature ⇒ no proof — but a verifier may decline in silence, so decision accountability is structurally unreachable). Safeguard 6 is the first invariant to constrain the *counterparty* rather than the operator; it is orthogonal to operator-blindness and reinforces Safeguard 2 (the signature is over the itemized request) while complementing Safeguard 5 (exit rights say you may leave; the receipt says why you were pushed). The mechanism is specified normatively in **ZKC §2.2, §5.5–§5.8** and is enforced for any ZKC predicate or bundle used with ZKA.

A conforming ZKA deployment MUST NOT require an operator, proxy, indexer, prover, predicate provider, compliance service, or settlement administrator to receive `masterSeed`, spending keys, note plaintext, or custody of Disclosure Receipts in order for an agent to hold, receive, spend, or withdraw ZKA notes. Remote services MAY assist with indexing, verification, proving, or signing only when they receive public inputs, encrypted material, viewing-limited material, or delegated authority that is insufficient for unilateral spending.

| # | Invariant | Audit Check |
|---|-----------|-------------|
| 1 | Predicate Pluralism | No hardcoded predicate-provider addresses or privileged roles in contract code |
| 2 | Minimal Disclosure | SDK defaults emit single-predicate proofs; composites require explicit opt-in |
| 3 | No Revocability | No admin/pausable/force-transfer paths in note-management contracts |
| 4 | Open-Source Predicates | Predicate inspection mandatory before proof generation in SDK flow |
| 5 | Exit Rights | Unshield/withdraw functions contain no compliance-gating conditional logic; operators and services cannot require custody of `masterSeed`, spending keys, or note plaintext |
| 6 | Verifier Accountability | SDK refuses unauthenticated requests by default; declared purpose is a bound public input under the purpose-bound proof context; receipts are holder-custodied and operator retention is absent |

## 2. Cryptographic Primitives

### 2.1 Hash Function

ZKA uses **Poseidon2** over the BN254 scalar field for all circuit-facing hash operations. The canonical implementation is `noir-lang/poseidon` v0.3.0's `Poseidon2::hash`, backed by Noir/Aztec/Barretenberg's Poseidon2 permutation and optimised for UltraHonk constraints. Its state width is **4**: three rate lanes and one capacity lane. `H_2`, `H_3`, and `H_4` below name the number of message fields supplied to this same width-4 sponge; they do not select width-2, width-3, or width-4 permutations.

For a message of `n` field elements, the canonical sponge places `n * 2^64` in the capacity lane, absorbs up to three message fields per permutation, and returns state lane zero. The length-bearing IV makes the message arity part of the hash definition; for example, `H_1(x) != H_2(x, 0)`.

Domain separation is construction-specific. A tagged construction prepends

```
deriveFieldTag(tag) = LEInteger(Blake2b-512("ZKA-Domain-" || UTF8(tag))) mod r
```

as specified by **AFP-KDC v1.0.2 §A.3**. Implementations MUST use the pinned field constants and MUST NOT substitute direct UTF-8-to-field encoding, big-endian digest interpretation, another Blake2 variant, or an unprefixed digest. Untagged constructions are explicitly identified below; the mere use of Poseidon2 does not imply a leading domain field.

**Key-derivation hashing** — the derivation of the spending, viewing, proof, and credential-binding keys, the address, and the credential commitment, and the domain tags `zka/spending`, `zka/viewing`, `zka/proof`, `zka/address`, `zkc/credential`, `zkc/binding` — is **defined by AFP-KDC v1.0.3 §A.4 and §A.6** using the immutable v1.0.2 profile and is not restated here. See §2.2.

**Operational (non-derivation) hashing** remains defined by this specification. ZKA defines one operational domain tag:

```
H_2(H_2(DOMAIN_ZKA_NULLIFIER, commitment), sk)  → nullifier
```

`DOMAIN_ZKA_NULLIFIER = deriveFieldTag("zka/nullifier")`. Per the AFP-KDC tag-collision rule (§A.4), it does not collide with a registered KDC or sibling-protocol tag and remains owned by ZKA. The two-layer note commitment and binary Merkle parent in §2.3–§2.4 are deliberately untagged, fixed-arity constructions pinned by the protocol vectors.

> **Compatibility boundary (informative).** Active ZKA proofs use Poseidon2 over BN254. Proofs and artifacts built over Poseidon/Pallas are not compatible, even when they use the same domain-tag strings. AFP-KDC v1.0.2 defines the active derivation; relocating that definition does not create another field, hash, or derivation profile.

### 2.2 Key Hierarchy

ZKA key derivation is defined by **AFP-KDC v1.0.3 §A.6** (AFP.dev, `docs/kdc_specification.md`) using the immutable v1.0.2 profile. ZKA does not restate the derivation; a conforming ZKA implementation MUST derive keys per AFP-KDC v1.0.2. The 32-byte seed is interpreted as an unsigned **big-endian** integer reduced modulo BN254.Fr before any derivation hash.

KDC takes a 256-bit master seed and derives the spending key (`sk`), viewing key (`vk`), proof key (`pk`), address (`addr`), credential binding key (`cbk`), and credential commitment (`holderCommitment`). Two KDC derivation facts are load-bearing for this specification (KDC §A.6):

- `cbk = H("zkc/credential", seed)` derives from the **seed**, not from `sk` — it is a sibling of the spending key, not a descendant. This is what allows credential ownership to be proven without exposing spending authority.
- The ZKA `address` and the ZKC `holderCommitment` derive along **separate paths** from the same seed and are unlinkable without it. The §5.2 identity-binding circuit proves the link in zero knowledge precisely because the link is otherwise unrecoverable.

**Seed provenance.** The 256-bit seed supplied to KDC is, in a standalone ZKA deployment, a master seed generated directly. Under AFP entity identity (AFP §4.3), it is a **per-entity sub-seed** `M'` derived from the tenant master seed via KDC §A.5. KDC key derivation does not distinguish the two cases; ZKA circuits that take a `masterSeed` private input (e.g. §5.2) accept whichever the deployment uses.

The normative `KeyHierarchy`, `deriveKeys`, and unlinkability definitions are in AFP-KDC v1.0.2 §A.6; ZKA does not define alternate forms.

**Aztec mapping** (for Aztec native deployment, §8):

| ZKA Key | Aztec Equivalent |
|---------|-----------------|
| `masterSeed` | App-siloed nullifier hiding key `nhk_app` |
| `spendingKey` | `H("zka/spending", nhk_app)` |
| `viewingKey` | `H("zka/viewing", spendingKey)` |
| `credentialBindingKey` | `H("zkc/credential", nhk_app)` — sibling of `spendingKey` |

### 2.3 Notes

```typescript
interface Note {
  asset: AssetDescriptor;    // Multi-asset support
  value: BoundedUnsigned;    // Hidden in proofs; bound selected by the deployment profile
  recipient: ZKAAddress;
  randomness: Scalar;        // BN254 scalar field element
  commitment: Commitment;    // H_2(H_3(asset_commitment, value, recipient), randomness)
  nullifier: Nullifier;      // Revealed when spent
  memo: Uint8Array;          // Up to 512 bytes, encrypted
}

interface AssetDescriptor {
  settlement: SettlementType;
  assetId: AssetId;
  decimals: u8;
  metadata?: { symbol: string; name: string };
}

type SettlementType = "ethereum" | "aztec" | "native";

type AssetId =
  | { type: "ethereum",  address: Address }
  | { type: "aztec",     assetId: Hash }
  | { type: "native",    id: Hash };

function computeCommitment(note: Note): Commitment {
  const assetCommitment = H_2(DOMAIN_ZKA_ASSET, canonicalAssetIdField(note.asset));
  const inner = H_3(assetCommitment, field(note.value), note.recipient);
  return H_2(inner, note.randomness);
}

// Standalone and other non-Aztec deployments only; §8.1 delegates Aztec spends.
function computeNullifier(note: Note, sk: SpendingKey): Nullifier {
  return H_2(H_2(DOMAIN_ZKA_NULLIFIER, note.commitment), sk);
}
```

`DOMAIN_ZKA_ASSET = deriveFieldTag("zka/asset")`. The settlement-specific canonical asset-id projection is defined by the applicable deployment or bridge profile. The inner and outer note-commitment hashes are untagged; their distinct fixed arities and nesting are normative.

`BoundedUnsigned` is a profile-selected unsigned integer domain. Each deployment profile MUST publish its width and inclusive maximum. Active note values are in `1..=maximum`; zero is reserved for an inactive or absent fixed-width slot. Before every `Field`-to-unsigned-integer conversion, an implementation MUST range-check the source value against its profile domain. This applies to deposits, transfers, withdrawals, popped input-note values, and change outputs. Conservation arithmetic MUST fail closed on aggregate overflow and MUST NOT truncate or wrap.

The Aztec-native ZKA/Pay profile selects `u128` with `maximum = u128::MAX`, so it accepts active values in `1..=u128::MAX`. The Base pool's `2^120 - 1` limit and any other narrower limit are profile-specific, not cross-environment cryptographic bounds. An adapter or import/export profile that targets a narrower destination MUST reject a value above the destination maximum before narrowing; it MUST NOT truncate, wrap, saturate, or otherwise silently coerce it.

#### 2.3.1 Note randomness generation

For every active output note, the holder implementation **MUST** generate `randomness` internally from an operating-system cryptographically secure random number generator. Sampling **MUST** cover the complete BN254 scalar field by rejection sampling canonical 32-byte representatives; modulo reduction of a narrow, biased, deterministic, user-supplied, or protocol-derived input is not conforming. Zero is never a valid active-output randomness value. Inactive fixed-width output slots continue to use zero.

A production SDK, wallet, bridge adapter, or rotation path **MUST NOT** accept caller-supplied note randomness. It **MUST** reject any reuse it can detect before proof construction, including reuse from an input note and repetition between active outputs in one transaction. A holder implementation **MUST** retain a bounded non-reversible in-process fingerprint window for values it generates so a recent accidental repeated CSPRNG output fails closed without unbounded memory growth. Deterministic constructors MAY exist only in an explicitly non-production test-vector build and **MUST** reject zero.

The transfer circuits enforce only witness-visible safety checks: each active output randomness is nonzero and differs from every active input and earlier active output randomness in the same transition. These constraints do **not** prove entropy, unpredictability, CSPRNG use, or uniqueness against notes absent from the witness; those remain generation-boundary obligations.

Randomness, note openings, and their reuse fingerprints are private material. Errors, logs, events, debug formatting, and telemetry **MUST NOT** include them. Generation failures use a stable redacted error and fail closed. Preparation and submission APIs that span multiple calls **MUST** retain the exact opening in holder memory (or holder-controlled encrypted storage); they MUST NOT regenerate an opening after publishing its commitment. A post-send transport, receipt, or event-decoding failure **MUST** return recoverable holder state containing that exact opening and any known transaction hash rather than a bare error that discards them. Settlement adapters **MUST** reconcile or resubmit only the exact retained transaction; they MUST NOT rebuild it with fresh note randomness. Confirmation requires a matching canonical settlement event for the retained note commitment (and transaction hash when known).

### 2.4 Merkle Tree

```typescript
interface MerkleTree {
  depth: 32;                   // Supports 2^32 notes
  hashFunction: "Poseidon2";   // BN254 field
  root: Hash;
  leaves: Commitment[];
  nextIndex: u32;
}
```

Merkle path verification uses the untagged binary parent `H_2(left, right)` over the depth-32 path (`zka_lib::compute_merkle_root`). Path-index bits are consumed least-significant-bit first across tree levels. The empty leaf is zero and the depth-32 empty root is obtained by 32 applications of `H_2(empty, empty)`. Conforming implementations MUST use this Poseidon2 construction and MUST NOT substitute a Pedersen-based Merkle helper.

The canonical append source for a ZKA deployment MUST be the settlement contract, settlement validity predicate, or deployment-defined append log that authorizes note creation. Balance servers, wallets, mirrors, and indexers MAY maintain local Merkle trees, but they MUST be reconstructable from the canonical append source and MUST NOT be authoritative for leaf order or root validity.

Every deposit, transfer, bridge import, or settlement action that creates a ZKA note MUST append that note commitment exactly once in deterministic settlement order. The leaf index is the zero-based append position in that canonical order. If multiple commitments are created by one settlement action, their intra-action order MUST be specified by the deployment profile and MUST be stable across all clients.

Canonical append events MUST expose enough public or holder-authorized data for clients and indexers to reconstruct the tree:

```typescript
interface CommitmentAppendEvent {
  commitment: Commitment;
  leafIndex: u32;
  previousRoot: Hash;
  newRoot: Hash;
  context: Hash; // deployment, chain, asset-domain, and circuit-domain binding
}
```

A verifier, settlement contract, or validity predicate MUST accept Merkle roots only from a deployment-defined `acceptedRootSet`. The deployment profile MUST define stale-root handling as either:

- the latest `N` canonical roots, where `N >= 1`; or
- roots no older than a configured block-height, epoch, or wall-clock window.

Roots outside the accepted window MUST be rejected with a machine-readable stale-root error. Rejection of a stale root MUST NOT invalidate the note; the holder can regenerate a Merkle path against an accepted root and resubmit.

## 3. ZKA/Pay: Private Transfers

### 3.1 Transfer Circuit (`zka_transfer`)

**Circuit constraints (in Noir):**

1. Input note Merkle membership
2. Nullifier correctness: derived from commitment + spending key
3. Ownership: input note recipient matches derived address
4. Output commitment correctness
5. Value conservation: `input.value == output.value`, `output.value > 0`
6. Asset conservation: `input.asset == output.asset`, asset commitment matches
7. Context binding: `context` is a non-zero public input. The deployment profile defines its derivation. The verifier MUST derive the expected value independently from its own authenticated state and MUST NOT take it from transaction data.

This circuit is single-input, single-output and value-preserving: it cannot split or merge notes. Value split and merge are defined by the ZKA/Pay `zka_pay_transition` circuit (§3.4: up to two inputs and three ordered outputs), within that profile's separate pool state domain. The circuit requires the note value to be non-zero and range-checks the input and output values to the u64 balance domain `[0, 2^64)`, so an active value is in `1..=2^64 − 1` and a field-wrapped value is rejected. A deployment profile that publishes a narrower maximum MUST still range-check against that maximum before every `Field`-to-unsigned conversion (§2.3).

**Reference artifact.** Earlier `zka_transfer` artifacts recomputed the Namada consensus context that ADR-0016 retired. The current artifact implements constraint 7 directly: `context` is a non-zero public input, and the circuit derives nothing else from it.

```typescript
interface TransferProof {
  publicInputs: {
    nullifier: Nullifier;
    outputCommitment: Commitment;
    merkleRoot: Hash;
    context: Hash;             // Profile-defined, verifier-derived replay context (constraint 7)
    assetCommitment: Hash;     // H_2(DOMAIN_ZKA_ASSET, canonicalAssetIdField(asset)) (§2.3)
  };
  privateInputs: {
    inputNote: Note;
    inputMerklePath: MerklePath;
    spendingKey: SpendingKey;
    outputNote: Note;
  };
  proof: UltraHonkProof;
}
```

### 3.2 Withdrawal Circuit (`zka_withdrawal`)

Consumes a note and **reveals** the withdrawal amount, the asset commitment, and the external recipient. Used for bridge exits (ZKA shielded pool → external chain).

Per Safeguard 5 (§1.6), the withdrawal circuit MUST NOT take any compliance predicate, credential, or binding proof as an input or constraint. Exit to self-custody is unconditional.

```typescript
interface WithdrawalProof {
  publicInputs: {                // exactly six BN254 field elements, in this order
    nullifier: Nullifier;        // [0]
    merkleRoot: Hash;            // [1]
    withdrawalAmount: Field;     // [2] Revealed; equals the consumed note's value
    assetCommitment: Hash;       // [3] Revealed; the asset field inside the note commitment (§2.3)
    externalRecipient: Field;    // [4] Revealed; non-zero destination
    context: Hash;               // [5] Bound as a public input; not constrained in-circuit
  };
  proof: UltraHonkProof;
}
```

The circuit proves input-note Merkle membership, nullifier correctness, and ownership as in §3.1, and constrains `withdrawalAmount` to equal the consumed note's value. It also requires `withdrawalAmount` and `externalRecipient` to be non-zero. It applies no other range constraint to `withdrawalAmount`: it does not range-check the value against a profile domain (§2.3). The §2.3 range-check obligation remains with every component that converts the value to an unsigned integer, including the settlement contract. The circuit does not constrain the value of `context`; the settlement contract MUST compare it with its deployment context (§7.1.2).

### 3.3 Root Update Circuit (`zka_root_update`)

Used by deployments that anchor an append-only commitment tree on an external rollup or L1 contract. Proves that a claimed `newRoot` is the correct Poseidon2 incremental insertion of the public deposit list followed by a prover-supplied private blob-commitment list into a prior accepted `prevRoot`. The proof preserves the order of the supplied values, but by itself does not prove that the private list came from published blob data and therefore does not prevent omission or substitution of blob commitments.

```typescript
interface RootUpdateProof {
  publicInputs: {
    prevRoot: Hash;
    newRoot: Hash;
    prevTotal: u64;                       // commitments folded so far
    newTotal: u64;                        // commitments folded after this update
    blobKzgCommitment: Hash;              // legacy-named non-zero proof tag; not a blob binding
    depositCommitments: Hash[];           // ordered by on-chain event-log position
  };
  privateInputs: {
    blobCommitments: Hash[];              // prover-supplied; not bound to blobKzgCommitment
    intermediatePaths: MerklePath[];      // one path per insertion, depth = MERKLE_DEPTH (32)
  };
  proof: UltraHonkProof;
}
```

**Circuit constraints (in Noir):**

1. Count consistency: `newTotal - prevTotal == depositCommitments.length + blobCommitments.length`
2. Deterministic interleave order: deposit commitments first (in event-log order), then blob commitments (in blob-payload order)
3. Incremental insertion: fold each commitment in order into the Merkle tree starting from `prevRoot` using `intermediatePaths`; the final fold MUST equal `newRoot`
4. Hash function: Poseidon2 over BN254 per §2.1
5. Tree depth: `MERKLE_DEPTH = 32` per §2.4
6. Legacy blob-tag check: `blobKzgCommitment` is a public input and MUST be non-zero; this binds only the exact tag value into the proof and establishes no KZG opening, blob preimage, or relation to the private `blobCommitments`

The `blobKzgCommitment` public input is not sufficient to bind the private values folded by this circuit. The immutable Base APLBridge passes a caller-supplied value directly into this public-input slot and never executes `BLOBHASH`; the circuit independently accepts any non-zero value. Consequently, that deployment and circuit establish no blob data-availability or blob-to-leaf binding property. A successor claiming blob data availability MUST compare the same-transaction `BLOBHASH` result on-chain and verify that the blob's canonical contents encode the private commitments folded by the proof.

A successor profile claiming EIP-4844 data availability MUST (1) obtain the blob versioned hash with `BLOBHASH` in the same blob-carrying transaction and compare it with a proof-bound public input, and (2) verify a cryptographic relation showing that the ordered commitment projection decoded from the blob's canonical announcement log equals the exact private commitments folded into `newRoot`. A `BLOBHASH` comparison alone binds the transaction to a blob, not the circuit's private witness values to that blob.

### 3.4 Immutable Base WETH9 Pool Profile

**Strategic status (informative).** This is an interim, non-production EVM deployment profile, not ZKA's strategic flagship or a production-certified target. The Aztec-native, owner-direct ZKA/Pay profile is the strategic flagship, subject to the official Aztec resolution of the Alpha V5 proving-system vulnerability and the other activation gates (audit qualification among them) in [ADR-0010](adr/0010-aztec-flagship-and-production-gates.md). This status statement changes neither this profile's normative circuit, state, or nullifier requirements nor its historical evidence.

ZKA/Pay defines an additive, immutable, single-asset settlement profile for Base WETH9. Its four circuits are:

| Circuit | Purpose |
|---|---|
| `zka_pay_deposit` | Binds a queued note commitment to the exact public WETH deposit amount and immutable pool/asset context; the contract stores the exact announcement-hash limbs with the queue entry. |
| `zka_pay_transition` | Proves a private payment with up to two inputs and three ordered outputs (recipient, change, fee). |
| `zka_pay_batch` | Recursively verifies payments, consumes the mandatory deposit prefix, advances both roots, and binds canonical batch calldata. |
| `zka_pay_withdrawal` | Consumes a note, advances the sparse nullifier root, and releases the proof-bound amount to the proof-bound Base recipient. |

Each accepted deposit appends the immutable tuple `(queue index, note commitment, amount, full announcement Keccak-256 high/low u128 limbs, depositor proof hash)`. A batch computes `deposit_prefix_digest` from that stored queue range. It separately computes `batch_data_digest` from strict- parsed canonical calldata, recomputes every deposit announcement hash, and requires the calldata commitment, amount, and both hash limbs to match the immutable queue entry before verification or state advancement. The batch circuit constrains the same five deposit fields into both digest streams.

The pool context is contract-derived, never a deployer-selected constructor value. It uses the exact UTF-8 tag `zka/pay/pool-context/v1` and the field-count-prefixed BN254 Poseidon2 fold over profile version, Base chain id, pool and asset addresses, asset commitment, full Keccak-256 limbs of all four circuit ids, and every frozen pool bound/depth. The complete ordered 22-field stream is normative in the pool SDD. Changing any field requires a new pool.

The complete identifiers, flattened public-input order, fixed bounds, tree depths, canonical `batchData` encoding, digest folds, and deterministic error taxonomy are normative in [the ZKA/Pay pool SDD](sdd/sdd_pay_pool.md). The machine-readable public-input encoders are `schemas/public-inputs/zka_pay_*.json`.

This profile supersedes neither the existing bridge circuits (§7) nor the existing ZKA note (§2.3). It uses the existing note-commitment semantics in a separate pool state domain with separate commitment/nullifier trees, escrow, verifiers, and accepted-root history.

## 4. ZKA/Coord v2: Profile-Bound Recursive Execution

ZKA/Coord v2 uses a fixed, 30-field execution receipt and bounded recursive DAG composition. The normative ABI, domains, profile-manifest contract, workflow-definition encoding, base and recursive cases, trust boundaries, failure codes, migration rules, and graduation gate are defined in [`docs/sdd/sdd_coord_v2.md`](sdd/sdd_coord_v2.md). The machine-readable ABI is [`schemas/public-inputs/zka_coord_v2.json`](../schemas/public-inputs/zka_coord_v2.json).

A final proof attests that every accepted step was proven by an execution profile in a verifier-selected policy, every active predecessor proof was cryptographically verified, and ordered predecessor outputs exactly equal the successor inputs. Workflow definition, instance, context, initial state, topology, profile artifacts, verification keys, assurance class, and inactive padding are all bound.

The three assurance classes are intentionally distinct: ZK-native execution, proof-producing external execution, and attested execution. The latter proves correct checking of a named trust anchor, not physical-world truth. ZKA defines no global profile allowlist.

ZKA/Coord v2 is the canonical pre-launch draft. It remains unaudited and not production-supported until the signed independent-review gate in `docs/security/coord_v2_audit_gate.md` passes. The four-field base circuit, three-field aggregate, and five-field bundle object are invalid and absent from active schemas, artifacts, registries, and SDK decoders. A conforming verifier MUST reject them; there is no legacy alias, width-based interpretation, or fallback verification key.

The public Rust API is canonical and unversioned (`CoordWorkflowBuilder`, `CoordProver`, `CoordVerifier`). Version markers remain mandatory in the cryptographic identities that prevent cross-protocol substitution, including the receipt/schema identifiers, circuit and artifact IDs, policy documents, manifest formats, and hash domains.

```typescript
interface CoordFinalPublicInputsV2 {

  graphCommitment: Field;
  proofNodeCount: u32;     // 1..=4096
  maxDepth: u32;           // 1..=32
}

interface CoordVerifierPolicyV2 {
  policyDocument: CoordVerifierPolicyDocumentV2;
  verifierPolicyRoot: Field;         // MUST equal recomputed policyDocument root

  workflowDefinition: CoordWorkflowDefinitionV2;
```

Serializers flatten `receipt` first and then the three aggregate fields, for a fixed total of 33 public field elements.

The reference verifier rejects raw recursive proofs above 65,536 bytes before backend dispatch and canonical JSON proof envelopes above 524,288 bytes before parsing. The typed `CoordProof` decoder also stops at byte 65,537 while streaming the proof array, so a compliance-bundle decoder cannot first allocate an attacker-selected oversized proof vector. Other implementations MUST publish and enforce equivalent conservative byte ceilings at every decoding and verification entry point. Proving time and memory still depend on active fan-in and recursion depth; implementations MUST publish measured bounds and MUST NOT claim workflow-length-independent proving cost.

An Aztec deployment is conforming only through an explicit, manifest-bound profile whose claim is tested independently. Kernel composition alone does not silently inherit the Coord v2 claim. The reference SDK publishes the off-chain UltraHonk path. An Aztec target additionally requires an independently registered profile and target verifier; no built-in Aztec Coord contract is provided. An EVM request fails with `UnsupportedTarget` until an exact EVM artifact and verifier are published, and MUST NOT fall back to an off-chain VK.

## 5. ZKA/Attest: ZKC Credential Integration (Normative)

This section defines ZKC credential integration in the ZKA protocol layer using Noir, UltraHonk, BN254, and Poseidon2. The constraint logic is expressed independently of deployment-specific performance parameters.

### 5.1 Identity Binding Model

The credential binding key links ZKA and ZKC identities without revealing either. ZKC v0.4 defines three presentation profiles. Legacy `linkable` v1 exposes the stable `holderCommitment`; v2 `scoped` exposes only `H("zkc/presentation-scope:v1", cbk, scopeId)`; v2 `anonymous` exposes neither handle (both presentation public inputs are zero). A scoped pseudonym is unlinkable across distinct scopes unless the principal discloses the link.

```
IDENTITY BINDING
================

ZKA Identity                    ZKC Identity
------------                    ------------

   address                      holderCommitment
      |                              |
      v                              v
  H("zka/address", vk)          H("zkc/binding", cbk)
      |                              |
      +--------------+---------------+
                     |
                     v
               masterSeed  (private witness only)
```

### 5.2 Identity Binding Circuits (`zka_credential`, `zka_transfer_binding_v2`)

Proves that a ZKC credential belongs to the same identity as a ZKA note, without revealing the master seed.

```
IDENTITY BINDING CIRCUIT
========================

Public Inputs:
  - noteCommitment: Commitment
  - holderCommitment: Hash
  - merkleRoot: Hash
  - context: Hash

Private Inputs:
  - masterSeed: Uint8Array[32]
  - note: Note
  - merklePath: MerklePath

Constraints:

1. KEY DERIVATION  (per AFP-KDC v1.0.3 §A.6, using the v1.0.2 profile)
   sk  = H("zka/spending", masterSeed)
   vk  = H("zka/viewing", sk)
   addr = H("zka/address", vk)
   cbk  = H("zkc/credential", masterSeed)
   // masterSeed is the per-entity sub-seed M' under AFP entity identity

2. NOTE OWNERSHIP
   note.recipient == addr
   note.commitment == noteCommitment
   verifyMembership(note.commitment, merklePath, merkleRoot)

3. CREDENTIAL BINDING
   H("zkc/binding", cbk) == holderCommitment

4. CONTEXT BINDING
   // context bound into the proof; prevents replay to a different
   // session/counterparty (context includes a session id)
```

```typescript
interface IdentityBindingProof {
  publicInputs: {
    noteCommitment: Commitment;
    holderCommitment: Hash;
    merkleRoot: Hash;
    context: Hash;
  };
  privateInputs: {
    masterSeed: Uint8Array;     // 32 bytes — proves ownership of both
    note: Note;
    merklePath: MerklePath;
  };
  proof: UltraHonkProof;
}
```

| Parameter | UltraHonk / BN254 |
|-----------|--------------------|
| Proving system | UltraHonk (Barretenberg) |
| Circuit size | 2^12 (padded size `N = 4096` of the generated EVM verifier for both `zka_credential` and `zka_transfer_binding_v2`, nargo 1.0.0-beta.25 / bb 5.0.0) |
| Proof size | 7,232 bytes for the EVM target, for both circuits (nargo 1.0.0-beta.25 / bb 5.0.0) |
| Verification | Unclaimed until a reproducible benchmark for the pinned toolchain publishes measurements |
| Solidity gas | Not measured for these verifiers |

The four-public-input `zka_credential` circuit above and the five-public-input `zka_transfer_binding` circuit in §5.3 are the frozen **linkable v1** profile. They remain accepted for backward compatibility.

For ZKC v0.4 v2 payments, `zka_transfer_binding_v2` is normative. It privately derives `sk = H("zka/spending", masterSeed)` and `cbk = H("zkc/credential", masterSeed)`, proves that `sk` owns the input note, and constrains `presentationPseudonym = H("zkc/presentation-scope:v1", cbk, scopeId)`. Its public inputs are `(nullifier, outputCommitment, merkleRoot, context, presentationPseudonym, scopeId)`. `scopeId` and `presentationPseudonym` MUST both be non-zero. Neither `masterSeed`, `cbk`, nor `holderCommitment` is public. An anonymous v2 presentation cannot bind a payment note to a credential subject and MUST be rejected for a payment bundle; it remains valid for a payment-free bundle when the bundle members retain the authenticated AFP session-context field projection and the ZKC proof separately matches AFP's authenticated presentation-purpose context.

**Issuer-signature verification is NOT duplicated here**: a ZKA binding proof attests only seed-linkage and note ownership; valid issuance remains in ZKC's per-credential circuits carried by `compliance.proofs[]`. `context` MUST bind the relevant replay-protection context. When carried by `afp:envelope:v1`, it equals `session_context_field`, the canonical BN254 projection of AFP's authenticated raw `session_context` defined in §5.4.

### 5.3 Combined Transfer + Binding Circuit

For efficiency, a combined circuit proves transfer validity and compliance binding in a single proof. `zka_transfer_binding` is the frozen linkable-v1 circuit:

```
COMBINED TRANSFER + BINDING CIRCUIT
===================================

Public Inputs:
  - nullifier: Nullifier
  - outputCommitment: Commitment
  - merkleRoot: Hash
  - context: Hash
  - holderCommitment: Hash      // for compliance binding

Private Inputs:
  - masterSeed: Uint8Array[32]
  - inputNote: Note
  - inputMerklePath: MerklePath
  - outputNote: Note

Constraints:
  // all transfer constraints from §3.1 (constraint 7: non-zero public context)
  +
  // binding constraint
  H("zkc/binding", H("zkc/credential", masterSeed)) == holderCommitment

Parameters (UltraHonk / BN254):
  - single proof for transfer + binding
  - padded circuit size 2^12 (N = 4096 in the generated EVM verifier)
  - EVM-target proof 7,232 bytes (nargo 1.0.0-beta.25 / bb 5.0.0)
```

`zka_transfer_binding_v2` uses the ordered public inputs `presentationPseudonym, scopeId` rather than `holderCommitment`. Like `zka_transfer_binding`, it takes the private `masterSeed` witness, not a spending key. Both binding circuits implement the §3.1 context rule: a non-zero public `context` whose expected value the verifier supplies, which is AFP's `session_context_field` under `afp:envelope:v1` (§5.2). The transfer spending key and ZKC v0.4 credential binding key are derived independently from that same secret in-circuit. This is the required v2 payment proof and prevents a prover from pairing a note owned by one subject with a scoped credential presentation from another.

### 5.4 Compliance Bundle

A Compliance Bundle is the unit a verifier checks: it may carry a ZKA transaction proof, zero or more atomic ZKC predicate proofs, the identity binding that links a payment note to a credential, and — optionally — a recursive ZKA/Coord work-attestation proof (§4). The bundle is a **ZKA-side envelope that wraps, but does not redefine,** ZKC compliance proofs: each element of `compliance.proofs[]` is an authoritative ZKC `zkc:proof:v1` (linkable) or `zkc:proof:v2` (anonymous/scoped) object from **ZKC v0.4**. The bundle envelope remains independently versioned as `zka:bundle:v1`; carrying the canonical pre-launch Coord v2 draft proof does not change that envelope version. The carried Coord, ZKC, and presentation-profile identities independently select their exact verifier/VK. Conforming cross-protocol implementations MUST select exactly one combination from the canonical `zka:protocol-family:2026-11-19.1` manifest and compatibility matrix; no match or multiple matches is invalid.

**Bundle profiles and the substantiveness rule.** Both `transaction` and `coord_proof` are OPTIONAL members, but a bundle MUST carry **at least one of `{transaction, coord_proof}`** — a bundle with neither attests no substantive ZKA-side work and is invalid (`EMPTY_BUNDLE`). `compliance.proofs[]` always *accompanies* a substantive proof (carried when the counterparty requires predicates); it is never the sole content of a valid bundle. The admissible profiles are:

- **(a) Payment bundle** — `transaction` present (`[+ compliance] [+ coord_proof]`), with `binding` linking the payment note to the credential. Existing payment-only encodings remain valid.
- **(b) Pure work-attestation bundle** — `coord_proof` present, `transaction` ABSENT. This is the transaction-absent ZKA v0.9.2-draft work-attestation bundle for non-monetary federation flows: **PRP reconciliation** (proving a Merkle root; no payment) and the non-monetary **VXP `vxp.reciprocal`** (data-for-data; no payment), both of which carry their evidence via AFP's `afp:envelope:v1` over this bundle (AFP v0.3.12-draft §12.7, ADR-0003). No payment ⇒ no note ⇒ `binding` is N/A and omitted.

The normative reciprocal compute/acknowledgement encodings and assurance boundaries are specified in [`sdd/sdd_coord_reciprocal_data_exchange.md`](sdd/sdd_coord_reciprocal_data_exchange.md). `vxp.reciprocal` MUST travel through the existing `zka:bundle:v1` pure work-attestation shape inside an authenticated AFP session, with the bundle `context` equal to AFP's derived `session_context_field`; it introduces no new envelope or session-binding primitive.
- **(c) Compliance-accompanied** — either of the above plus `compliance.proofs[]`, carried when the counterparty requires predicate attestations. Compliance proofs ride on a substantive bundle; they do not constitute one on their own.

`transaction` is OPTIONAL because non-monetary flows such as PRP reconciliation and `vxp.reciprocal` carry compliance/work evidence over `zka:bundle:v1` with no payment leg. Requiring a payment proof would make those flows unable to form a valid bundle. The substantiveness rule admits pure work-attestation while leaving every payment bundle valid.

The bundle is also the single ZKA-owned cryptographic payload that AFP's session envelope (`afp:envelope:v1`, AFP v0.3.12-draft §12.7) carries verbatim across a tenant boundary. The OPTIONAL `coord_proof` and OPTIONAL `transaction` members do not change the `zka:bundle:v1` envelope identity: payment/compliance bundles remain valid instances, and transaction-absent bundles use the same explicitly optional field encoding.

**Authenticated context split is mandatory.** Verification MUST receive both context classes from the authenticated AFP outer interaction; it MUST NOT copy either expectation from the untrusted bundle or proof. AFP retains its raw authenticated `session_context` as exact `X_` plus 64 lowercase hexadecimal digits. Let `d` be those 32 payload bytes and let `q = 21888242871839275222246405745257275088548364400416034343698204186575808495617`. The fixed projection is `s = OS2IP_BE(d) mod q`; `s = 0` is invalid, without retry or substitution, and otherwise `session_context_field` is `s` serialized as exact `0x` plus 64 lowercase hexadecimal digits. The raw `X_...` value remains the AFP session identifier and is authenticated before projection; modulo-field equality is never session authentication. `session_context_field` binds the bundle members, while the selected `afp:zkc-presentation-context:v2` mode authenticates the separate `presentation_proof_context` used by ZKC. A scoped v2 payment additionally requires a verifier-selected `scopeId`. A malformed or zero projection, a session-member mismatch, or a ZKC proof/presentation-context mismatch is invalid.

```text
session_context = require_exact_afp_X_digest(afp.authenticated.session_context)
session_context_field = nonzero_bn254_projection(session_context)
presentation_proof_context = afp.authenticated.context(
    selector = "afp:zkc-presentation-context:v2",
    trust_flow = verifier_selected_authenticated_flow,
    purpose = verifier_selected_authenticated_purpose,
)

require(bundle.metadata.context == session_context_field)
if bundle.transaction is present:
    require(bundle.transaction.publicInputs.context == session_context_field)
if bundle.coord_proof is present:
    require(bundle.coord_proof.receipt.context == session_context_field)
for envelope in bundle.compliance.proofs:
    require(envelope.metadata.context.value == presentation_proof_context)
    if envelope.version == "zkc:proof:v2":
        for predicate in envelope.proofs:
            require(predicate.publicInputs.proof_context == presentation_proof_context)
```

For `afp:zkc-presentation-context:v2`, the authenticated AFP record contains exactly `kind`, `purpose`, `credential_subject_aid`, `session_context`, `apr_verifier_aid`, `presentation_profile`, and `scope_policy`; its `session_context` member is the original authenticated `X_...` value, not `session_context_field`. Its trust-flow selector is one of `afp:trust-flow:telemetry`, `afp:trust-flow:bilateral`, `afp:trust-flow:introduction`, or `afp:trust-flow:open-federation`, and `purpose` MUST equal that selector. For the scoped profile, `scope_policy` MUST be `protocol:afp:` followed by a nonempty AFP-owned profile-policy hash; it is `null` for anonymous or linkable profiles. `presentation_proof_context` is `int_be(SHA-256(RFC8785_JCS_UTF8(record))) mod q`, serialized as exactly 32 big-endian bytes of lowercase `0x` hexadecimal. A zero reduction is invalid. The selector is part of the matched protocol-family tuple. A verifier MUST recompute this field before proof verification and MUST NOT substitute either session-context representation for `presentation_proof_context`. This selector and comparison change no `zka:bundle:v1` wire shape or ZKC circuit public-input ABI.

**AFP verifier-result boundary.** The AFP adapter result has exactly the three top-level members `{proof_context, credential_subject_aid, proven_predicates}`. `proven_predicates` is a nonempty ordered array of exact six-member records: `{predicate_id, predicate_version, root_class, root_authority_identifier, attestation_window, subject_aid}`. Every member is present; unavailable values are explicit `null`. The identifier is versioned, `predicate_version` is the matching nonempty decimal suffix, and duplicate identifiers are invalid. The adapter verifies each complete normalized record against its verified evidence snapshot, rather than accepting an identifier-only claim. At the presentation-policy seam, only `predicate_id`, `predicate_version`, `root_class`, and `root_authority_identifier` have authenticated policy comparands; `attestation_window` and `subject_aid` remain free there and receive their specified Introduction bindings later. A non-null `attestation_window` is `{starts_at, ends_at}` in canonical whole-second UTC with `starts_at < ends_at`.

The verifier's sibling `required_predicate_policy` comparand is not part of the result. It contains unique sorted `accepted_predicate_ids`, `required_predicate_ids`, and accepted `{root_class, root_authority_identifier}` pairs. Accepted predicates are nonempty, required predicates are a subset, and the telemetry instance-attestation predicate is accepted only when at least one root pair is pinned. AFP telemetry has a broader closed catalog; this conformance profile requires `afp.telemetry.instance_attestation.v2`. That record requires a nonempty subject AID, a valid window, and an accepted root-authority pair whose class is exactly one of `root:build-provenance`, `root:tee-attestation`, or `root:publisher-manifest`. For other predicates, root class and root authority are null; bilateral, introduction, and open-federation otherwise retain caller-policy-selected predicate pluralism. Structural validation never substitutes for AFP's KEL/delegation/revocation resolution or its later request-window/presenter checks.

The CI-gated AFP presentation-seam classification is:

| Proven-predicate field | Class at presentation seam | Independent comparand / later binding |
|---|---|---|
| `predicate_id` | bound | required/accepted predicate policy and exact verified ZKC statement |
| `predicate_version` | bound | version suffix of `predicate_id` and exact verified statement |
| `root_class` | bound | null for ordinary predicates; supported class and accepted class/authority pair for telemetry v2 |
| `root_authority_identifier` | bound | null for ordinary predicates; accepted class/authority pair plus AFP authority resolution for telemetry v2 |
| `attestation_window` | free | shape and presence are validated here; Introduction later binds it to its authenticated request window |
| `subject_aid` | free | shape and presence are validated here; Introduction later binds it to the authenticated presenter/entity-or-instance rule |

“Free” means the presentation seam has no independent equality comparand for that value; it does not mean an application may skip the specified shape, presence, or later Introduction checks.

Separate non-result adapter-assurance metadata MUST identify an issuer-authenticated AID claim or independently verified companion subject-binding proof as the basis for `credential_subject_aid`; it MUST NOT be copied from ZKC evidence. A generic ZKC KYC or jurisdiction predicate alone cannot establish that subject and MUST be rejected. The optional predicate `subject_aid` is not universally equal to this result subject because an instance predicate may identify an entity or one of its instances. When a bundle binds a payment subject, it MUST equal the verified result `credential_subject_aid`. This is an AFP adapter contract only: ZKC v0.4.1 circuits, verification keys, proof envelopes, and public-input ABI remain unchanged.

**Verifier selection is part of verification.** For each ZKC predicate, the parser resolves the exact `(envelopeVersion, presentationProfile, proofType)` tuple and supplies it to the ZKC verifier/VK registry; an unsupported or mismatched tuple fails closed. Structural parsing validates a versioned `proofType` identifier but MUST NOT infer its version from the envelope suffix: registry policy owns valid mixed-version tuples, including selective-disclosure v1 in a v2 presentation envelope. For the payment binding, the verifier receives the exact selected circuit plus the complete ordered public statement: five fields for `zka_transfer_binding` v1 or six fields for `zka_transfer_binding_v2`. A verifier that has no configured cryptographic implementation MUST reject; structural proof-byte checks are not proof verification.

**ZKM carriage boundary.** `zka:bundle:v1` currently defines no `authorization` or ZKM member. An implementation MUST NOT place a ZKM proof in `compliance.proofs[]`, reinterpret `coord_proof` as mandate authorization, or claim recursive ZKM carriage through this envelope. §5.4.1 selects direct settlement for the ZKA/ZKM integration and leaves this bundle unchanged: ZKM's separately versioned, spend-conjoined statement remains outside `zka:bundle:v1` and is accepted only through a ZKM-aware settlement target and ZKM's deployment registry, which apply the ZKA note/nullifier effects and the ZKM mandate transition atomically.


```typescript
async function verifyComplianceBundle(
  bundle: ComplianceBundle,
  requirements: ComplianceRequirements,
  trustPolicy: TrustPolicy,
  authenticated: {
    bundleContext: Hash;               // Under AFP, recomputed session_context_field.
    presentationContext: {
      profile: "afp:zkc-presentation-context:v2";
      value: Hash;
    };
    selectedScopeId?: Hash;
  }
): Promise<VerificationResult> {
  const errors: VerificationError[] = [];

  // Expectations are verifier-supplied, never learned from `bundle`.
  if (bundle.metadata.context !== authenticated.bundleContext)
    errors.push({ code: "BUNDLE_INCONSISTENT", details: "unauthenticated bundle context" });
  if (bundle.transaction !== undefined &&
      bundle.transaction.publicInputs.context !== authenticated.bundleContext)
    errors.push({ code: "BUNDLE_INCONSISTENT", details: "transaction context mismatch" });

  // 0. Substantiveness — a valid bundle MUST carry at least one
  //    substantive proof. `compliance.proofs[]` alone is never sufficient.
  if (bundle.transaction === undefined && bundle.coord_proof === undefined)
    errors.push({ code: "EMPTY_BUNDLE",
                  details: "bundle carries neither transaction nor coord_proof" });

  // 1. ZKA transaction proof (OPTIONAL) — verify only when present.
  //    A pure work-attestation bundle (profile b) has no transaction leg.
  if (bundle.transaction !== undefined) {
    if (!(await verifyUltraHonk(bundle.transaction)).valid)
      errors.push({ code: "INVALID_ZKA_PROOF" });
  }

  // 2. ZKC predicate proofs — each predicate MUST be open-source and
  //    inspectable per Safeguard 4; trustPolicy enumerates accepted
  //    predicate providers (no canonical provider — Safeguard 1).
  //    Verified over whatever proofs ARE present (the set MAY be empty).
  if (!(await verifyZKCProofs(bundle.compliance, requirements, trustPolicy, authenticated)).valid)
    errors.push({ code: "INVALID_ZKC_PROOF" });

  // 3. Binding links the payment NOTE <-> ZKC credential. It is present IFF
  //    `transaction` is present (no payment ⇒ no note ⇒ nothing to bind).
  if (bundle.transaction !== undefined) {
    if (bundle.binding === undefined) {
      errors.push({ code: "BUNDLE_INCONSISTENT",
                    details: "transaction present but binding absent" });
    } else {
      const statement = resolveBindingStatement(bundle.transaction, bundle.binding);
      if (!(await verifyManifestSelectedBindingProof(statement)).valid)
        errors.push({ code: "INVALID_BINDING" });

      // 4. Bundle consistency — note<->credential checks, IFF the relevant
      //    members are present.
      if (bundle.binding.transactionCommitment !==
          bundle.transaction.publicInputs.outputCommitment)
        errors.push({ code: "BUNDLE_INCONSISTENT", details: "tx commitment mismatch" });
      for (const envelope of bundle.compliance.proofs) {
        const target = resolveZkcVerifierTarget(
          envelope.version, envelope.presentationBinding?.profile, envelope.proofs);
        if (!target.valid)
          errors.push({ code: "INVALID_ZKC_PROOF", details: "unsupported version/profile" });
        else if (!bindingSubjectMatchesEnvelope(bundle.binding, envelope))
          errors.push({ code: "BUNDLE_INCONSISTENT", details: "binding subject/profile mismatch" });
      }
    }
  } else if (bundle.binding !== undefined) {
    // A transaction-absent bundle MUST NOT carry a note<->credential binding:
    // there is no note for it to bind (it would be unanchored/meaningless).
    errors.push({ code: "BUNDLE_INCONSISTENT",
                  details: "binding present without a transaction" });
  }

  // When `transaction` is absent, no note<->credential binding exists. The
  // bundle and any Coord proof remain anchored to authenticated.bundleContext.
  // Each ZKC proof is independently checked against
  // authenticated.presentationContext, whose value AFP derives from the
  // authenticated flow, purpose, session, subject, verifier, profile, and scope
  // policy. Neither context class may be substituted for the other.

  // 5. Freshness — bundle expiry AND ZKC accumulator-epoch recency.
  //    Per ZKC v0.4 §6.2, each ZKC proof's accumulator epoch MUST be
  //    within MAX_EPOCH_LAG = 10 epochs of the verifier's current epoch.
  if (bundle.metadata.expiresAt < Date.now())
    errors.push({ code: "BUNDLE_EXPIRED" });
  if (!zkcEpochsWithinLag(bundle.compliance.proofs, /*MAX_EPOCH_LAG*/ 10))
    errors.push({ code: "ZKC_EPOCH_STALE" });

  // 6. ZKA/Coord work-attestation (OPTIONAL) — verify only when present.
  //    A bundle without coord_proof is unaffected by this step.
  if (bundle.coord_proof !== undefined) {
    // 6a. Verify the manifest-bound Coord v2 recursive artifact. This authenticates
    //     profile-adapter and predecessor proofs plus their constrained receipts;
    //     step 6c still applies the verifier's own policy and completion definition.
    //     An Aztec proof is accepted only through an independently conforming
    //     manifest-bound profile (§8.2), never by kernel composition alone.
    if (!(await verifyManifestBoundUltraHonk({
            proof: bundle.coord_proof.proof,
            publicInputs: bundle.coord_proof.receipt,
            circuit: "zka_coordination_v2_recursive",
            artifactPolicy: trustPolicy.coord })).valid)
      errors.push({ code: "INVALID_COORD_PROOF" });

    // 6b. Context binding — the coordination proof MUST share the bundle context
    //     (and hence, under AFP, session_context_field for the carrying envelope, §12.7).
    if (bundle.coord_proof.receipt.context !== bundle.metadata.context)
      errors.push({ code: "BUNDLE_INCONSISTENT", details: "coord context mismatch" });

    // 6c. Verifier-selected policy and complete-workflow checks. A prover's
    //     public policy root or workflow root is never authoritative.
    const coord = trustPolicy.coord;
    const receipt = bundle.coord_proof.receipt;
    if (coord === undefined) {
      errors.push({ code: "COORD_V2_PROFILE_POLICY", details: "no verifier Coord policy" });
    } else {
      const definition = validateAndHashCoordWorkflow(coord.workflowDefinition);
      const policy = validateAndHashCoordPolicy(
        coord.policyDocument,
        coord.acceptedAssuranceClasses,
        coord.acceptedProfileManifestHashes);
      if (!definition.valid ||
          receipt.workflowDefinitionHash !== definition.root ||
          receipt.stepId !== definition.completionStepId)
        errors.push({ code: "COORD_V2_INCOMPLETE_WORKFLOW" });
      if (!policy.valid || policy.root !== coord.verifierPolicyRoot ||
          receipt.verifierPolicyRoot !== policy.root)
        errors.push({ code: "COORD_V2_PROFILE_POLICY" });
      if (definition.valid && !definition.steps.every(step =>
            coord.acceptedAssuranceClasses.includes(step.assuranceClass)))
        errors.push({ code: "COORD_V2_ASSURANCE" });
      if (definition.valid && !definition.steps.every(step =>
            coord.acceptedProfileManifestHashes.includes(step.profileManifestHash)))
        errors.push({ code: "COORD_V2_ARTIFACT" });
      if (coord.expectedWorkflowInstanceId !== undefined &&
          receipt.workflowInstanceId !== coord.expectedWorkflowInstanceId)
        errors.push({ code: "COORD_V2_SCOPE", details: "workflow instance mismatch" });
      if (receipt.initialStateCommitment !== coord.expectedInitialStateCommitment ||
          (definition.valid &&
           definition.initialStateCommitment !== coord.expectedInitialStateCommitment))
        errors.push({ code: "COORD_V2_SCOPE", details: "initial state mismatch" });
      if (coord.expectedContext !== undefined && receipt.context !== coord.expectedContext)
        errors.push({ code: "COORD_V2_SCOPE", details: "verifier context mismatch" });
    }
  }

  return { valid: errors.length === 0, errors };
}
```

**Conditional verification.** Each member is verified IFF present, and the transaction-dependent consistency checks fire only when a payment leg exists:

- `transaction` verified IFF present (step 1).
- `binding` is the payment-note↔credential link: it MUST be present when `transaction` is present and MUST be absent when `transaction` is absent. Its transaction commitment MUST match the payment output. Every carried compliance envelope MUST match the binding's version, profile, and subject handle: v1/linkable compares `holderCommitment`; v2/scoped compares both `presentationPseudonym` and `scopeId`. v2/anonymous and mixed/cross-profile sets are invalid for payments. With no payment there is no note, so this binding is N/A.
- `compliance.proofs[]` is verified over whatever proofs are present (the set MAY be empty).
- `coord_proof` verified IFF present (step 6), with `context == metadata.context` (step 6b) and verifier-selected profile/workflow/artifact policy plus designated completion-step checks (step 6c).

**Identity anchor when `transaction` is absent.** A pure work-attestation bundle still binds to a single party identity, but **not** through the note↔credential binding (which is N/A without a note). The bundle and Coord receipt retain the authenticated AFP `session_context_field` anchor derived from the raw session identifier. Any ZKC predicate proof has its own authenticated presentation-purpose anchor selected by `afp:zkc-presentation-context:v2`; its proof context is not a session member and is compared only with AFP's `presentation_proof_context`. Both comparisons are mandatory, so a cross-flow or cross-purpose presentation cannot be attached to an otherwise valid transaction-absent bundle.

A bundle verification failure has exactly one permitted consequence: the counterparty declines the interaction. It MUST NOT trigger any note invalidation, freeze, or force-transfer (Safeguard 3). This holds for a `coord_proof` failure as well: a failed (or context-mismatched) coordination proof means the work-attestation is not accepted, never that any note is affected.

> **Canonical Coord carriage (AFP v0.3.12-draft §12.7, ADR-0003).** The optional `coord_proof` member makes `zka:bundle:v1` the single ZKA-owned wire format for ZKA/Coord work-attestation proofs alongside Pay/compliance/binding proofs. A profile MUST NOT author another bundle wire format; it places a ZKA bundle inside `afp:envelope:v1`. The receipt context equals the bundle metadata context, which AFP derives as `session_context_field` from its authenticated raw `session_context`. The pre-launch five-field coordination carriage is invalid.

AFP remains responsible for session framing, routing, authentication, and `session_context` binding; ZKA remains responsible for the bundle and carried proof semantics.

### 5.4.1 ZKM Authorization Carriage and Atomic Settlement

ZKM spend mandates are an **optional interaction authorization**, not a ZKA note-validity rule. A conforming ZKA deployment MAY expose the interface in this section; an ordinary transfer, deposit, withdrawal, force exit, or bundle that does not opt into ZKM MUST remain valid under exactly the pre-ZKM rules.

**Canonical carriage decision — direct settlement.** ZKA selects the ZKM reference path: the settlement target verifies one `zkm:spend-conjoined:v2` UltraHonk proof and applies its ZKA and ZKM effects in one target transaction. The proof already contains the ZKM SPEND transition, the ZKA value-note spend, and the policy predicate over shared wires; a second ZKA transaction proof MUST NOT be accepted as a substitute for that structural conjunction. This revision does **not** add a `zkm_authorization` (or any other ZKM member) to `zka:bundle:v1`. Merely placing unrelated ZKA and ZKM proofs in an envelope is non-conforming.

The spend-conjoined public vector is exactly 14 BN254 field elements, in this order (integers are zero-extended to one field element):

```text
(kind, mandateNullifier, mandateSuccessorCommitment,
 mandateSecondSuccessorCommitment, mandateRoot, revocationRoot,
 revocationScheme, currentTime, settlementContext, assetId,
 zkaNoteRoot, zkaNullifier, zkaRecipientCommitment, zkaChangeCommitment)
```

`kind` MUST equal ZKM SPEND (`0`), `revocationScheme` MUST equal `2`, and `mandateSecondSuccessorCommitment` MUST be the zero sentinel. The verifier MUST flatten named inputs in this order; it MUST NOT sort fields or accept an alternate encoder. ZKM keeps the private `amount` off this vector. The two ZKA output commitments bind it inside the proof.

**Staged positive-spend cutover.** ZKM's successor rev-13 statement set
`sha256:f367e0504bcbbe4ca2a150f9c56a7640d5ed21bdb9dec1c1ce4acaa6e023ab49`
requires `amount > 0` in-circuit and corrects the mandate-only policy-witness
diagnostics. Its spend vector remains the 14 fields above, including both ZKA
output slots. A positive full-note spend still produces a freshly blinded
zero-value change commitment; the target MUST apply both outputs atomically.
A target adopting this exact surface MUST atomically select its reviewed spend
verifier/VK and retire the prior spend key, preserving the single shared
mandate-nullifier set and ZKA nullifier state. A proof under the rev-12 key is
not evidence of the positive-amount constraint. The staging intent alone does
not change the accepted family epoch or activate a settlement deployment;
adoption remains conditional on the coordinated successor publication.

`revocationScheme` names the ZKM revocation-accumulator profile the proof's non-membership witness was constructed against. Scheme `2` is the depth-254 full-identifier exclusion tree; scheme values `0`, `1`, and `3..255` are invalid and MUST be rejected before verification. The target treats it as a statement discriminator it checks, never as a policy dial it selects: the registry-pinned VK already accepts exactly one scheme, and the explicit equality check makes a scheme mismatch a deterministic rejection rather than a verification failure whose cause is opaque.

**Verifier, registry, and binding checks.** Before changing state, a conforming target MUST perform all of the following:

1. Select the one deployment-registry entry for `zkm:spend-conjoined:v2`, including its exact VK hash, verifier artifact, public-input encoder, ZKM version, settlement target, and asset profile. The value-moving entry MUST be immutable or version-pinned for the lifetime of the adapter. A proof verified by `zkm:mandate-only:v2`, a possession, disclosure, revocation, control-attestation, or unknown VK MUST NOT reach a value-moving entry point.
2. Require `settlementContext` to equal the target's own non-zero ZKA deployment context. The fixed spend-conjoined circuit also proves that the consumed mandate commits to this domain. A caller-supplied context is never authoritative.
3. Require `assetId` to equal the target registry's asset identifier. The fixed circuit proves that the consumed ZKA note and both output notes use the corresponding ZKA asset commitment. A settlement adapter MUST document the exact `assetId`↔ZKA asset-commitment mapping it accepts.
4. Recognize `mandateRoot` in its own recent mandate-root history, `zkaNoteRoot` in its own recent ZKA note-root history, and `revocationRoot` in its own ZKM revocation-root history. It derives the revocation epoch from that history and applies ZKM freshness policy. Post-cutover, that history MUST contain only scheme-2 roots published at or after the ZKM activation epoch; a scheme-1 root MUST NOT be recognized, relabelled, or reinterpreted under scheme 2. For this expiry-only statement profile, capture the authenticated target clock `targetTime` and its immutable or version-pinned `zkmProofTimeWindow()` policy `W` once for this attempt. Accept `currentTime` iff `currentTime >= targetTime` and `currentTime - targetTime <= W`, checking the first inequality before subtraction and never computing an overflowing `targetTime + W`. `W = 0` retains exact-clock acceptance; a disclosed positive window permits inclusion delays without reproving. `revocationScheme` MUST equal `2`.
5. Verify the proof against the registry-selected spend-conjoined VK and the exact vector above. That circuit is the same-note/same-holder proof: its public `zkaNullifier` consumes the ZKA note proven under `zkaNoteRoot`, while one private holder secret derives the mandate holder key, the consumed ZKA note address, and the ZKA nullifier key. Host code MUST NOT emulate this private equality with caller-supplied holder fields.
6. Reject if `mandateNullifier` is already present in the target's **single mandate-nullifier set for `settlementContext`**, shared by every accepted ZKM VK, or if `zkaNullifier` is already present in ZKA's nullifier state. The target owns both authoritative sets: the mandate set is shared across all accepted statements, verification keys, and adapter deployments, and the ZKA set is the same state used by ordinary transfers and exits. Per-VK or per-adapter mandate-nullifier sets are forbidden: the same mandate note could otherwise be replayed once per statement/VK or redeployment. Adapter replacement or VK rotation MUST preserve that state.

All field elements MUST be canonical BN254 representatives. Required roots, nullifiers, context, asset, and live output commitments MUST be non-zero. The SPEND kind discriminator and unused second mandate-successor slot are zero; the `uint64 currentTime` MAY also be zero when accepted by the authenticated clock profile. `revocationScheme` remains `2`.

**Expiry clock and quantization.** The circuit's existing `currentTime` proves only `currentTime < expiry`; it is a chosen upper bound on inclusion time, not a report of execution time. The host rule above therefore establishes `targetTime <= currentTime < expiry` while retaining the unchanged 14- and 9-element public vectors and their VKs. A deployment MUST disclose the clock source, time unit, quantization and `W`, authenticate both getters through its target binding, and keep clock/policy values stable throughout one settlement attempt, including root-history admission and effect application. A changed window requires an explicitly pinned policy version; callers MUST NOT choose it. A target lacking the new getter fails closed. The reference test target defaults to `W = 0` and uses explicit test policy versions to exercise positive windows and a moving clock. These optional-ZKM clock checks MUST NOT gate ordinary transfers or exits.

For an expiry-only target using physical time `t` and quantum `Q > 0`, both expressed in the artifact's common time unit, the authenticated clock MUST round **up**: `targetTime = Q * ceil(t / Q)`. Compute the round-up with checked arithmetic and reject an unrepresentable result before narrowing; never wrap or clamp a clock. Flooring is unsound for an unaligned expiry because it can accept after the real expiry by up to `Q - 1` units. Ceil rounding conservatively ensures `t <= targetTime <= currentTime < expiry`; it may shorten the useful window, which the deployment MUST disclose. Expiry, proof time, target time and `W` MUST all use the same declared unit. This rule provides no future `not_before` guarantee: rounding up can cross a lower bound before physical time reaches it. A future interval artifact must separately prove `not_before <= t_lo` and `t_hi < expiry` and accept only `t_lo <= now <= t_hi` under its specified clock semantics. Such an interval changes the statement/vector and belongs to a separate artifact version; this profile adds no lower-bound field or implicit future-validity claim.

**ZKM statement version boundary (fail-closed).** The statements selected here are the post-cutover ZKM ones. `zkm:spend-conjoined:v1` and `zkm:mandate-only:v1` — the 13- and 8-element ABIs of the previous revision, whose witnesses were built against the depth-128 low-half revocation tree and which carry no `revocationScheme` — are valid only under pre-cutover ZKM keys and roots. A post-cutover deployment registry MUST omit both and MUST NOT reinterpret, upgrade, or cross-verify a v1 proof. It MUST NOT accept a v1 vector under a v2 VK or a v2 vector under a v1 VK. The two profiles never coexist in one registry: ZKM's cutover is atomic, so before activation only the v1 profile is accepted and at or after activation only scheme 2 and its v2 keys are. A deployment that must remain on pre-cutover ZKM is conforming to the previous revision of this section and MUST document that it is pre-cutover; it is not conforming to this one, and a target MUST NOT present the two as interchangeable.

**Atomic state transition.** After every precondition and proof check succeeds, the target applies exactly these five effects as one transaction:

1. check-and-insert `mandateNullifier` into the shared ZKM nullifier set;
2. check-and-insert `zkaNullifier` into ZKA nullifier state;
3. insert `mandateSuccessorCommitment` into the mandate tree;
4. insert `zkaRecipientCommitment` into the ZKA note tree; and
5. insert `zkaChangeCommitment` into the ZKA note tree.

**Target obligations.** `applyZkmSpend` MUST check-and-insert both nullifiers against that target-owned state; `applyZkmMandateTransition` MUST check-and-insert the mandate nullifier against the same mandate set. A duplicate MUST revert the entire operation. An adapter-local cache is never authoritative. The target MUST accept these effect calls only from registered adapters whose exact statement/verifier/VK lanes it authenticates; arbitrary callers MUST NOT insert effects. Each settlement attempt MUST honor withdrawal of authorization for its selected lane, either by a per-call adapter registry check or an equivalent target check. Revoking a lane MUST prevent its already-deployed adapters from settling; authorization of an unrelated lane cannot substitute. This control applies only to optional ZKM interactions and MUST NOT pause, gate, or change ordinary ZKA exits.

**Permanent per-tree commitment uniqueness.** Every stateful SPEND or mandate transition MUST reject a live output commitment already present at any prior position in its target tree, including commitments whose notes have since been consumed. It MUST also reject equal live output commitments within the operation. The target owns separate permanent mandate and ZKA commitment ledgers, shared across all statements, VKs, adapter deployments and ordinary insertion paths for the corresponding tree. Namespace separation is by target tree: an equal byte string in the mandate tree does not itself forbid that value in the ZKA tree. A zero mandate-successor sentinel is not a leaf and MUST NOT enter either ledger. Consuming a note, changing the clock/policy, rotating a key or replacing an adapter MUST NOT prune or reset these ledgers. Every duplicate failure MUST roll back the whole operation, including any earlier nullifier, leaf, counter, root or event write; silently dropping one duplicate output while accepting a spend or transition is forbidden.

Before admitting an existing settlement context, the target MUST initialize these ledgers from complete authenticated commitment history, including consumed notes, and preserve the target's canonical finality/reorganization semantics. An empty cache at adapter cutover is not a complete history. A target unable to establish the full historical uniqueness guarantee MUST fail closed; this requirement does not authorize a production migration or repair. Ordinary ZKA insertions MUST enforce the same ZKA ledger, while ordinary withdrawals and force exits remain independent of mandate, expiry and revocation gates and MUST NOT delete historical commitment entries. `ZKAEthPool` remains outside this optional direct-settlement profile as classified below.

A correctly verified issuance of a known mandate commitment MAY instead be a **whole-operation idempotent no-op**: no new leaf or position, counter, root, success event or new inclusion receipt. Proof, exact verifier/VK and deployment/domain validation MUST precede that decision; a known commitment alone is not issuance authorization. An append-only tree that appends the known commitment again has changed state and is not a no-op. This issuance rule MUST NOT be used to ignore a duplicate output of a stateful spend or mandate transition. The SDK's `record_verified_mandate_issuance` and `record_verified_zka_note` are trusted driver hooks only after the corresponding proof and domain checks; they model the shared permanent ledgers, not permissionless admission methods.

**Payee acceptance and receipt freshness.** A payee MUST authenticate the accepted target/profile and canonical inclusion of a **new** recipient commitment, with its target finality policy, and verify that the supplied opening recomputes that exact commitment for the expected asset, value and recipient under the authenticated asset-slot mapping. A valid proof or correctly opening historical note alone is insufficient evidence of a new payment: position-independent nullifiers make a repeated commitment the same note identity, not fresh spendable value at another index. The payee's wallet MUST check available authoritative spentness using its privately derived note nullifier and retain local anti-replay state for the target/domain, commitment and accepted inclusion/payment association. Unavailable spentness or incomplete finality/freshness evidence MUST NOT be represented as a verified fresh payment. These checks remain holder-side; they MUST NOT publish note openings, spending keys, private nullifiers or lineage identifiers merely to demonstrate receipt freshness. A later legitimate spend does not undo the earlier payment, but presenting its proof, opening or inclusion again does not create another payment.

**Public settlement evidence and holder receipts.** Every accepted SPEND or mandate-only transition MUST publish enough public evidence to recover its complete settled public vector, exact statement, full public proof bytes, verifier address, authenticated target address, and full VK identifier without decoding transaction calldata or obtaining an execution trace. For this EVM profile, the VK identifier is `(scheme = ultra_honk, transcript_target = evm, vk_hash = exact bb VK hash)`; the `evm` target selects the Keccak transcript. A statement identifier is separate from that tuple. The adapter emits `ZkmSettlementEvidence` with indexed `(mandateNullifier, statementId, target)` and non-indexed `(verifier, proofScheme, transcriptTarget, vkHash, publicInputs, proof, successorLeafIndex, secondSuccessorLeafIndex, targetTime, proofTimeWindow)`. Scheme and transcript are the right-zero-padded ASCII `bytes32` literals `ultra_honk` and `evm`; `publicInputs` is the exact 14- or 9-element ordered vector above, including roots, scheme, the proven expiry upper bound `currentTime` and context. The appended `uint64 targetTime` and `uint64 proofTimeWindow` are the captured authenticated clock and window actually used for admission; neither is reread after effects. They permit independent acceptance and revocation-history replay even when proof time is in a later epoch. Replay MUST use `targetTime` with the target's pinned clock/policy version, not reinterpret the future `currentTime` as the clock at execution. The legacy `ZkmSpendSettled` and `ZkmMandateTransitionSettled` events remain unchanged and MUST be accompanied by the evidence event.

Every possession proof actually accepted by the companion-bearing entry point, including an optional companion for another kind, MUST additionally emit `ZkmPossessionEvidence` with the same three indexed keys, its own `zkm:possession:v1` statement/verifier/VK tuple, exact three-element public vector and full proof bytes. These records MUST be emitted only after all verified effects and returned-position checks succeed. A failed proof, withdrawn lane, target failure, invalid index response or later revert MUST leave no accepted evidence or partial state. A digest or retrieval URL alone cannot replace the public proof bytes: it cannot independently re-verify a missing proof.

A verifier MUST authenticate the chain, adapter emitter, target and registry version rather than trust an event signature from an arbitrary contract. Its settlement inclusion coordinate is the canonical EVM `(block, transactionIndex, logIndex)` together with transaction/block identity and the target's finality policy; a caller, relayer or multicall's address is not the ordering key. Paired evidence is matched within the accepted transaction by authenticated emitter/target, consumed nullifier and exact companion equations. Collision adjudication uses the transition's referenced revocation root and the target's canonical order under ZKM §7.2; a later revocation remains prospective and cannot retroactively invalidate an accepted transition.

This is complete **public settlement evidence**, not a complete holder receipt. ZKM §5 still requires holder-retained successor/recipient note openings, delegation identity material and any complete proof-envelope metadata actually asserted by the receipt. The adapter never receives the full JSON envelope and cannot reconstruct its metadata. Those private receipt fields, authority secrets and private lineage `root_id` MUST NOT be emitted in transition evidence. Proof bytes and already-public vectors add no note openings or lineage identifier. A holder combines these logs and immutable registry material with its retained private artifacts to discharge the receipt's independent proof-verification and commitment-opening rules; no operator cooperation or archive trace is required for the public settlement portion.

**Truthful mandate insertion positions.** Both target callbacks return `MandateLeafIndices { uint64 successorLeafIndex; uint64 secondSuccessorLeafIndex; }`, allocated by the target's authoritative depth-32 mandate tree in the same atomic operation as all effects. Each non-zero successor MUST return its actual inserted position in `[0, 2^32 - 1]`; zero is a valid position. Each zero successor slot MUST return `NO_LEAF_INDEX = 2^64 - 1`, which is outside the valid tree range, and MUST allocate no leaf. SPEND therefore returns one live position and one sentinel, and RETIRE returns two sentinels. Two live slots MUST have distinct positions. The adapter MUST validate zero-slot/sentinel equivalence, depth bounds and index aliasing before publishing evidence; it MUST NOT invent indices, infer them from adapter-local counters or substitute an unavailable position. Capacity exhaustion and invalid return data MUST revert the complete transition, including earlier insertions and nullifier writes. The reference test target uses an ordered append-only leaf journal to demonstrate positions and rollback; that journal alone is not a production Merkle-root implementation.

A void-return legacy callback cannot satisfy this ABI: return-data decoding MUST fail closed and roll back its effects. Adopting this evidence profile also requires the target to withdraw authorization from every legacy adapter route that can settle without publishing the required evidence or returning truthful positions, preserving both target-owned nullifier sets. A new adapter does not itself fence an old authorized adapter. Ordinary ZKA transfers and exits remain outside this optional-ZKM activation.

**Target state representation (current 14-field profile).** A deployment binding MUST identify the target's authoritative ZKA nullifier representation and the note/asset-commitment profile used by both its ordinary value paths and ZKM. The proven `zkaNullifier` is the full canonical field value, not a truncated slot, tuple hash, or adapter-local replay key. The target MUST check its absence and insert it atomically into the same state ordinary transfers and exits consult. An internal tree index is not an alternative public nullifier encoding; a slot collision MUST fail closed rather than overwrite a consumed leaf. The public `zkaNoteRoot` authenticates the note-commitment tree; it is not a nullifier root or an update witness.

| Target representation | Admission under this direct-settlement profile |
|---|---|
| Exact full-nullifier set (mapping, set, or transactional table) | Eligible when every value path shares that authoritative set and the target can atomically check-and-insert the proven nullifier with all commitments. |
| Authenticated tree whose target maintains enough state to compute/check insertion itself | Eligible only when the target establishes absence of the exact proven nullifier and updates its canonical tree/root in the same transaction; ordinary paths must consume that updated state. |
| Root-only, proof-authoritative state whose update requires a proof carrying previous/next nullifier roots | Not supported by the current 14-field vector: it carries neither root transition nor its update witness. Admission requires separately specified, coordinated statement/target-profile work. |

The representation is an additional conformance condition, not an opt-in granted by recognizing a ZKM VK. A target MUST NOT replace a required root transition with an adapter map, accept an unchecked caller-selected root, or repurpose a commitment/root slot as missing nullifier-update evidence. A root-based design remains subject to all target ownership, replay, and atomicity obligations above.

**Asset-slot binding.** In this profile, `assetId` is the registry-selected identifier; the ZKA value-note asset slot is `C_asset = poseidon2(DOMAIN_ZKA_ASSET, assetId)`, as computed by `zka_lib::compute_asset_commitment` (`noir/zka_lib/src/lib.nr`) and ZKM's mirrored `compute_zka_asset_commitment`. The value-note commitment is `poseidon2(poseidon3(C_asset, value, recipient), randomness)` and its nullifier is `poseidon2(poseidon2(DOMAIN_ZKA_NULLIFIER, note_commitment), spending_key)`. The deployment binding MUST pin these exact primitives and the `assetId`/`C_asset` pair. Consumed and emitted notes, the target's accepted commitment roots, and ordinary transfers/exits MUST use that same profile. A field-representable asset number alone does not establish this binding.

**Existing `ZKAEthPool` status.** The current `contracts/ethereum/ZKAEthPool.sol` is not a ZKM-capable target for this profile and does not implement `IZKMSettlementTarget`. It stores ZKA nullifiers solely through `nullifierRoot`; its 13-field batch proof and eight-field withdrawal proof bind the previous/next nullifier roots before the pool advances state. The ZKM vector above cannot drive those transitions. Independently, the pool sets `ASSET_COMMITMENT = keccak256(abi.encode(chainid, asset)) & (2^248 - 1)` directly, whereas the ZKM value-note leg applies the domain-tagged asset wrapper above. Setting `assetId` to the pool slot, or aligning an asset label alone, does not adapt its nullifier-update boundary. A separate reviewed profile/statement and target integration is needed before claiming that pool's notes can be consumed or its outputs withdrawn through ZKM. The mapping-based Solidity test target and SDK model demonstrate host obligations, not production pool compatibility. This classification does not alter the pool's existing value and withdrawal validity rules.

Either all five effects and their events become visible, or none do. A target MUST use a transactional state primitive (for example an EVM transaction, a database transaction, or copy-on-write staging) and MUST propagate any late tree, capacity, or callback failure so the two nullifiers roll back with every commitment insertion. It MUST NOT acknowledge, queue, or emit a successful effect before the whole transition commits. All five effects use the target's ordinary ZKA finality semantics.

The non-value entry point verifies `zkm:mandate-only:v2` over its distinct 9-element ABI and MAY update only mandate nullifier/commitment state:

```text
(kind, mandateNullifier, mandateSuccessorCommitment,
 mandateSecondSuccessorCommitment, mandateRoot, revocationRoot,
 revocationScheme, currentTime, settlementContext)
```

`kind` MUST NOT be SPEND (`0`) and `revocationScheme` MUST equal `2`. Its ABI contains no ZKA note root, ZKA nullifier, ZKA output commitment, or asset ID; this absence is a deployment-safety property, not a host-side policy flag. The two vectors are the same nine leading elements plus the spend-conjoined form's five-element ZKA value leg, so an implementation MUST distinguish them by registry-selected VK and vector length, never by content sniffing. Both entry points MUST share the mandate-nullifier set.

**Possession companion for handoff.** Every DELEGATE_FULL (`kind = 3`), DELEGATE_PARTIAL (`kind = 4`), and ROTATE (`kind = 5`) MUST NOT settle without a second proof under the target registry's distinct `zkm:possession:v1` verifier/VK. Its public vector is exactly three non-zero canonical BN254 elements, in this order: `(mandateSuccessorCommitment, mandateNullifier, settlementContext)`.

These are the mandate transition's own first successor, consumed nullifier, and authenticated target context. An adapter MUST derive this vector from the transition or compare all three companion fields for exact equality before verification; a caller-selected independent vector is never sufficient. The first successor is the delegate leg for every delegation, including DELEGATE_PARTIAL with zero or dust retained capability. Its matching companion is mandatory regardless of the retained leg. A supplied companion for any other transition MUST also be verified. SPLIT (`1`) and RETIRE (`2`) need no companion. A possession proof alone authorizes no effect and MUST NOT substitute for either the mandate-only transition or the spend-conjoined proof.

The possession verifier/VK is independently pinned and authenticated by the target registry, with authorization checked for each attempt using that lane. Both proofs MUST succeed before the target consumes the nullifier or inserts any successor. Missing, invalid, mismatched, or withdrawn companions MUST leave all state and events unchanged. Possession-lane withdrawal MUST NOT gate transitions that do not use it, SPEND, or ordinary ZKA exits. The reference adapter adds `settleMandateTransitionWithPossession`; its existing companion-free entry rejects kinds `3`, `4`, and `5`. The SDK reference applies the same rule through `settle_mandate_transition_with_possession` and its companion-free wrapper.

**Companion activation.** Deploying a corrected adapter does not revoke an older registered adapter that accepted handoffs without possession. Before activating this rule against existing roots, the target MUST withdraw callback authorization from every legacy adapter that accepts any delegate or rotation without possession, including an optional kind-`4` route (or provide equivalent admission enforcement with no surviving legacy mandate route). It MUST preserve the target's consumed nullifier sets across that activation. Because mandate callbacks carry effects rather than a transition kind, accepting old adapter bytecode in parallel is unsafe. An operator that cannot fence the old route MUST fail closed rather than claim companion enforcement. This optional-ZKM activation does not change the ordinary exit boundary below.

**Exit and revocation boundary.** The ordinary ZKA withdrawal and force-exit entry points MUST NOT call the ZKM adapter, inspect mandate state, require a ZKM proof, or consult ZKM revocation/expiry. Revoking or exhausting a mandate can prevent a future mandate-authorized interaction; it cannot invalidate, freeze, redirect, or delay any ZKA note or exit. ZKM RETIRE concerns remaining mandate authority and is not the ZKA custody exit.

**ZKM rev13 insertion and publication boundary.** A target adopting the rev13 statement surface MUST implement ZKM §7.1's verified accumulator update separately from value settlement. It MUST verify `zkm:revocation-auth:v1` for issuance authority and the distinct `zkm:revocation-insertion:v1` continuity companion, matching their public identifier and settlement context. The companion vector is exactly `(root_id, previous_root, next_root, revocation_scheme, epoch, settlement_context)`; the scheme is `u8`, the epoch `u64`, and the other fields are canonical non-zero BN254 representatives. Each proof MUST use its exact registered statement/verifier/VK tuple. The continuity proof alone MUST NOT authorize revocation, mandate transitions, or any ZKA value effect.

For a new identifier, `previous_root` MUST equal the current accepted accumulator tip at execution, scheme MUST equal `2`, context MUST equal the authenticated target context, and epoch MUST equal `floor(target_time / T)` from the target's authenticated monotonic clock. The empty-to-full-id update, revoked-id record, new tip, root-history metadata and canonical-order publication event MUST commit atomically. A stale concurrent witness MUST fail without an accepted-insertion receipt and may be retried after witness refresh. An authorized duplicate identifier MUST be an idempotent no-op, including an exact replay in a later epoch; it MUST NOT publish another root or refresh historical-root age. Targets MUST NOT expose an arbitrary-root publication or rollback lane.

The recognized history MAY contain multiple ordered tips within one epoch. Its current tip has age zero across idle epochs; a superseded tip ages from the authenticated epoch in which it was replaced, with no later refresh. Unknown roots, epochs before activation, future epochs and roots older than the disclosed `staleness_max` MUST fail closed. The complete authenticated activation checkpoint and accepted full-id insertion log MUST be available for independent root and witness reconstruction. Migrated targets MUST follow the ZKM v2 migration runbook rather than bootstrap from an empty tree. Fees, resource bounds, witness-refresh retries, inclusion latency and publication availability MUST be disclosed; issuance authority does not limit the number of self-issued identifiers.

Revocation remains prospective in the target's canonical transaction order and subject to ZKM's disclosed effectiveness lag. These accumulator effects MUST NOT touch ZKA notes, ZKA nullifiers, received value, withdrawals, or force exits. Adoption requires the coordinated family statement-set publication and reviewed deployment registry; family epoch `zka:protocol-family:2026-09-10.1` alone pins rev12 and MUST NOT be represented as a rev13 activation. The reference insertion implementation and measurements are ZKM-owned artifacts and do not establish that an existing ZKA pool has enabled or qualified this path.

**Staged recipient-binding cutover.** The same exact successor statement set
corrects the recipient-address derivation in `zkm:spend-zkc-binding:v1` while
retaining its identifier and five-field public vector. A target adopting this
surface MUST atomically replace its registry-selected recipient-binding
verifier/VK and reject the prior key. The old key is not evidence of the
corrected AFP-KDC spending-key-to-address derivation. This replacement preserves
the authenticated settlement context, matched ZKA output and shared replay
state; the staging intent does not activate a deployment.

**`zka:bundle:v1` compatibility proof.** The JSON interface in §5.4, its version literal, substantiveness rule, verifier algorithm, error taxonomy, and all existing serialized instances are unchanged. The direct-settlement input is a separate target method and is never parsed by `verifyComplianceBundle`. Every payment-only `zka:bundle:v1` instance remains byte-for-byte valid, unknown ZKM carriage is not implied, and no envelope version bump is warranted. A future recursive/bundle path requires an explicitly specified member, registry binding, equality checks, atomic target transition, and compatibility decision; until then it is non-conforming.

The executable reference boundaries are `contracts/ethereum/ZKMAtomicSettlement.sol` and `src/zka-sdk/src/zkm/mod.rs`. The Solidity contract fixes separate immutable spend-conjoined, mandate-only, and possession verifier lanes, authenticates all three verifier/VK-hash pairs through the target registry at construction, rechecks each used lane on every call, and delegates authoritative nullifier check-and-insert to the target. The reference target in `test/ZKMAtomicSettlement.t.sol` owns the cross-adapter mandate set and the ZKA set shared with ordinary exits. The SDK model owns both sets in its target state, stages a cloned state, and publishes it only after every effect succeeds. They define the adapter contract, not a claim that every existing ZKA pool deployment has enabled ZKM.

### 5.5 Predicate Model

A **predicate** is an open-source compliance circuit that proves exactly one property (e.g. "holder is not on an OFAC SDN list", "holder is over an age threshold"). Predicates are published by independent, permissionless **predicate providers**.

- **Pluralism (Safeguard 1):** the protocol carries no canonical predicate set and no privileged provider. A verifier's `trustPolicy` enumerates which providers/predicates *it* accepts; different counterparties may accept different predicate sets.
- **Atomicity (Safeguard 2):** each `ZKCComplianceProof` proves a single predicate. A composite (multi-predicate) request MUST be expressed as separate proofs with separate, principal-readable consent.
- **Auditability (Safeguard 4):** predicate circuits MUST be published as inspectable Noir source, versioned, with a public review period before activation. An SDK MUST refuse, by default, to generate a proof against a predicate the agent cannot inspect. (Safeguard 4 is mirrored normatively in **ZKC v0.4 §1.4**, which mandates open-source/auditable predicate and credential-schema circuits, versioned publication with a public review period, and SDK refusal of opaque predicates by default with logged opt-in override.)

> **Proof-type registry is non-exclusive.** ZKC's Well-Known Identifier Registry and §3.1–3.6 schemas are references, not a closed allowlist. No type or provider is privileged or required, a verifier's `trustPolicy` MAY accept predicates outside the registry, and the protocol defines no mechanism for a canonical predicate set. ZKC well-known type IDs are permitted but never required, consistent with Safeguard 1.

### 5.6 Credential Lifecycle

> **Status: normative by reference to ZKC.** The binding, bundle, and predicate model (§5.2–5.5) are normative in this specification. ZKC owns the issuance, revocation, and accumulator-witness mechanics: the concrete issuer-bootstrapping and accumulator-witness-distribution protocols are specified normatively by the ZKC Specification §4 (Attestation Layer) and the **ZKC Issuer Adapter Protocol v1** (`ZKC/docs/zkc_issuer_adapter_protocol_v1.md`, with `schemas/issuer-metadata.schema.json` and a machine-checked conformance kit). ZKA references that protocol rather than redefining it.

**Issuance / Issuer Bootstrapping.** A ZKC credential is issued by a credential issuer (e.g. a KYC provider) binding an attestation to the holder's `cbk` via `holderCommitment = H("zkc/binding", cbk)`. The issuer never learns the holder's ZKA address or spending key. The issuer-bootstrapping protocol (issuer registration, issuer key publication, holder ↔ issuer attestation exchange) is REQUIRED for a conforming ZKC deployment and is specified normatively by ZKC (ZKC Specification §4 and the ZKC Issuer Adapter Protocol v1); ZKA references it rather than redefining it.

**Revocation.** Credential validity is tracked by a cryptographic accumulator. A predicate proof MUST demonstrate non-revocation by proving a current accumulator witness for the credential. Revocation MUST NOT be able to affect ZKA note validity (Safeguard 3) — a revoked credential causes counterparty refusal only.

**Accumulator Witness Update Distribution.** On any revocation the accumulator changes and all non-revoked holders need an updated witness. A conforming deployment MUST provide a witness-update distribution channel that does not deanonymize holders (e.g. publish epoch accumulator deltas that holders apply locally). The concrete distribution protocol is Draft.

### 5.7 Structural Requirements

The following are REQUIRED for a complete deployment. The note discovery, key custody, and key rotation/recovery requirements are normative; delegated proof generation remains Draft where marked.

- **Note Discovery Protocol.** A recipient MUST be able to discover incoming notes using only the incoming viewing key, without requiring a trusted indexer, operator, or sender-side out-of-band channel to reveal which notes belong to the recipient.

  Every deposit, transfer, bridge import, or settlement action that creates a ZKA note MUST publish an append-only note announcement. The deployment-specific carrier MAY be a smart-contract event, Aztec note log, APL event stream, or another authenticated append-only log, but clients MUST be able to reconstruct the same ordered announcement set from public or holder-authorized data.

  ```typescript
  interface NoteAnnouncement {
    commitment: Commitment;
    encryptedNoteCiphertext: Uint8Array;
    ephemeralPubkey: Uint8Array;
    viewingTag?: Uint8Array;
    context: Hash; // chain, deployment, asset, and circuit-domain binding
  }
  ```

  `encryptedNoteCiphertext` MUST encrypt the note plaintext, note randomness, asset/value metadata needed for spending, and any encrypted memo under a key agreement that the sender forms from its ephemeral secret and the recipient's public viewing/address material, and that the recipient can reproduce with its incoming viewing key. The announcement MUST NOT expose the recipient address, `masterSeed`, spending key, note plaintext, or linkable holder identity.

  Recipients scan announcements with their incoming viewing key and trial-decrypt candidate ciphertexts. Implementations SHOULD include a short Orchard-style `viewingTag` as a coarse filter to reduce scanning cost. The tag MUST be derived so that possession of the tag, announcement log, or indexer state is insufficient to identify the recipient without the incoming viewing key.

  Indexers MAY mirror, shard, and query the announcement log. They MUST NOT be authoritative for note ownership and MUST NOT learn which announcements a recipient accepts. A recipient MUST be able to recover note discovery from the append-only log plus its own viewing key even if all optional indexers are unavailable.

- **Agent Key Custody Model.** ZKA's default and required protocol posture is non-custodial. Agents or their principals own the KDC seed material, including `masterSeed` or the AFP-derived per-entity sub-seed `M'`, and derive spending, viewing, proof, address, and credential-binding keys locally or through a holder-controlled signer.

  A conforming ZKA deployment MUST NOT require `masterSeed`, spending keys, or unencrypted note plaintext to be held by a platform operator, CredentialProxy, BalanceServer, indexer, prover, predicate provider, or compliance service. Any hosted custody mode is a separate deployment/product profile and MUST NOT be represented as baseline ZKA conformance unless the host lacks unilateral spend authority, such as through holder-controlled remote signing, HSM/KMS policy controlled by the principal, MPC/TSS, or equivalent delegated signing.

  The ZKA SDK surface SHOULD support local encrypted keystores, OS keychain integrations, HSM/KMS-backed signers, remote signer adapters, viewing-key-only audit export, and explicit capability separation between spending authority and viewing/audit authority.

- **Key Rotation / Recovery.** Because `cbk` derives from the master seed, seed compromise orphans the credential binding. A conforming deployment MUST define a rotation/recovery path that re-binds existing credentials to a new seed without revealing the old↔new link on-chain. ZKC v0.4 §4.5 defines the required ZKC-Core credential rebind proof (`zkc:proof:credential_rebind:v1`) for holder-controlled migration from `oldHolderCommitment` to `newHolderCommitment`; issuer-specific migration tokens MAY optimize an integration but MUST NOT replace that core circuit.

  Routine rotation MUST use ordinary holder-controlled private self-transfers from old notes to an address derived from the replacement seed. The transfer and batch proof formats, encrypted announcements, calldata, events, and public state transitions MUST be indistinguishable in shape from ordinary ZKA/Pay activity: no rotation flag, migration circuit identifier, completion marker, or public old-to-new note mapping is permitted. SDKs MUST provide circuit-bounded batching and randomized local scheduling where latency permits; deployments MAY tune the local policy but MUST document it. Scheduling metadata MUST NOT enter a proof or transaction.

  For the Base WETH9 immutable-pool deployment profile, production SDK execution MUST use the manifest-bound `zka_pay_transition` / `zka_pay_batch` Noir circuits and that profile's ordinary immutable-pool submission path. Other settlement profiles MUST bind their production rotation circuits and ordinary submission path in the deployment-profile manifest and provide equivalent digest, root, nullifier, and finality validation. Simulated proof execution is not a conforming rotation path. Before proving, the client MUST validate the exact canonical batch-data digest and old commitment/nullifier roots and counters. After submission, status MUST be derived from canonical replay of accepted commitment roots, nullifiers, output commitments, and the deployment's finality policy—not from a local success flag or RPC receipt alone.

  Rotation state MUST be locally resumable and typed at least as `planned`, `proof_ready`, `submitted`, `retryable_submission`, `confirmed`, `retryable_stale_root`, `already_spent`, `missing_note_plaintext`, and `missing_merkle_path`. `proof_ready` means that a real batch proof was durably recorded before crossing the broadcast boundary. `retryable_submission` requires explicit holder confirmation that the indeterminate transaction and every known canonical replacement were dropped; unresolved or indeterminate broadcasts MUST remain `submitted` and MUST NOT collapse to `planned` or be automatically rebroadcast. A note is `confirmed` only when its nullifier and the batch's output commitments exist at the canonical finalized checkpoint. Before that checkpoint, a reorg MUST remove any noncanonical acceptance observation, but an indeterminate broadcast MUST remain `submitted` until canonical finalization, a finalized conflicting spend, or explicit holder confirmation that the transaction and every known replacement were dropped; only then may canonical replay select a retryable state. Finalized `confirmed` state is immutable under that synchronizer boundary. A stale root is retryable after rebuilding the witness against current state. A nullifier observed without the expected atomic batch outputs is terminal `already_spent`; a note whose plaintext or current membership witness cannot be reconstructed MUST be reported with the corresponding missing-data state rather than silently omitted. Durable diagnostics MUST contain no seed, spending key, note plaintext, recipient address, private path, or old-to-new note mapping.

  The replacement address and any ZKC v0.4 payment binding MUST derive from the same replacement `masterSeed`: `sk = H("zka/spending", newMasterSeed)`, `address = H("zka/address", H("zka/viewing", sk))`, `cbk = H("zkc/credential", newMasterSeed)`, and `presentationPseudonym = H("zkc/presentation-scope:v1", cbk, scopeId)`. Consequently an old-seed note cannot satisfy a transfer-binding-v2 presentation derived from the new seed. AFP/APL integrations MUST carry the ordinary new-seed payment bundle; a special rotation-completion attestation, if ever required, needs a separate ADR and MUST NOT be inferred from or added to settlement calldata.

  Credential rebinding is owned by ZKC and affects credential issuance and acceptance only. It MUST NOT affect ZKA note validity, custody, transferability, withdrawal, nullifier semantics, or revocation semantics. ZKA deployments that integrate issuer-assisted credential rebinding MUST require sealed/minimized issuer audit mappings for any retained old-holder-commitment to new-holder-commitment link. Such records MUST be access-controlled, encrypted or equivalently sealed at rest, purpose-limited to migration audit/compliance, retained for the minimum applicable period, and never published to settlement, indexer, note-discovery, compliance-bundle, or public-proof surfaces.

- **Delegated Proof Generation.** An agent MAY delegate proof generation to a prover service via encrypted witness transport such that the prover learns neither the witness nor the holder identity. Mechanism: Draft.

### 5.8 Aztec Composability

When deployed as an `aztec.nr` contract, an identity binding proof (§5.2) is composable with private DeFi within a single Aztec transaction via the kernel circuit call stack (see §8.4). `holderCommitment` is the stable ZKC holder anchor that linkable v1 presentations expose, not a pseudonym. An Aztec deployment MUST NOT publish `holderCommitment` (as a public function argument, public log, public state key or value, or nullifier) in a transaction that also publishes the holder's Aztec address or that the holder submits. Such a pairing links every linkable presentation of that holder to the address. The reference contracts (`aztec/zka_credential_aztec`, `aztec/zka_transfer_aztec`) have these public outputs:

- **Credential issuance** is authenticated by one issuer key that the credential contract pins at deployment and never changes. A holder can store a credential only with that issuer's ECDSA secp256k1 signature over the contract's issuance transcript, which binds the chain, the contract instance, the `holderCommitment` that the contract derives from the holder's own key, and every credential value. The issuer learns `holderCommitment` but not the holder's Aztec address, and the call publishes neither. Only such issuer-signed credentials can register or disclose. The pinned key is the whole issuer trust policy: there is no ZKC issuer registry, accumulator, validity window, or ZKC proof verification, so a registration is evidence of that issuer's signature only, not ZKC conformance.
- **Compliance registration** proves non-revocation in private. The holder proves that the revocation nullifier of their own `holderCommitment` is absent from the anchor block's nullifier tree. The only public output is the registering address, which the public compliance registry holds by design. The registration transaction expires one hour after its anchor block, which bounds the revocation lag.
- **Revocation** by the credential admin emits the inner nullifier `H2("zka/aztec/revocation/v1", holderCommitment)` (fixed-byte domain `zka-aztec-revocation-v1`) and publishes the revoked `holderCommitment` as a public statement about that anchor. It links the anchor to no holder address. Anyone who already holds the anchor can test whether it is revoked.
- **The compliance-gated transfer** reads the registry and the gate configuration in private. It enqueues no public call, so it publishes neither the recipient nor the fact that the gate ran. Registry and configuration changes take effect after a delay equal to the protocol's maximum transaction lifetime. With that delay, the private reads bound the expiration no lower than the kernel already bounds every private call, so a gated transfer's expiration equals a plain transfer's. While a gate configuration change is pending, gated transfers instead expire just before its public timestamp of change. That reveals the gated transfers of that deployment, but not their recipients. The admin controls that window. An emergency disable also waits for the delay.
- **Selective disclosure to a recipient** (`disclose_to`) delivers a note that carries `holderCommitment` to that recipient. This is not public, but the recipient learns the global anchor, so two recipients can link the holder. Deployments that need cross-verifier unlinkability MUST use ZKC scoped presentations instead.

Residual exposures remain:

- A private read obtains its witness from the node that serves the PXE. For a registration, that witness is keyed by the siloed revocation nullifier, which anyone who knows `holderCommitment` can compute. The same node usually relays the transaction that publishes the registering address, so that node can pair `holderCommitment` with the address. For a gated transfer, the node learns the recipient. Holders who need protection from the node MUST use a node they trust.
- A registration anchored before a revocation and included after it stands out as a candidate holder of the revoked anchor. The one-hour expiration bounds this window.
- Revocation does not remove an existing registration, and a repeat registration changes no state. Holders SHOULD NOT re-register on a schedule, because the stop of that schedule after a revocation links the anchor to the address.

## 6. Selective Disclosure

### 6.1 Balance Proof Circuit (`zka_balance`)

Proves that `note.value` is a genuine integer within a published `[low, high]` interval, without revealing the exact value and without consuming the note (no nullifier is emitted).
The circuit supports three comparison modes, canonicalized to a single saturating-interval encoding so that a solvency proof, a limit proof, and a range proof are all instances of the same statement rather than three unrelated ones.
A balance proof is an atomic single-property disclosure and is subject to Safeguard 2.

```typescript
interface BalanceProof {
  proof: UltraHonkProof;
  publicInputs: {
    merkleRoot: Hash;          // [0] ZKA state tree anchor (note membership; the note is NOT consumed)
    assetCommitment: Hash;     // [1] identifies the asset type the statement is about
    thresholdOrLower: Field;   // [2] canonical interval LOW bound
    upperBound: Field;         // [3] canonical interval HIGH bound
    proofType: Field;          // [4] comparison mode: 0 = value >= lower, 1 = value <= upper, 2 = range
    context: Hash;             // [5] verifier/session replay binding
  };
}
```

Comparison modes and the canonical saturating-interval encoding: proof type 0 is a solvency proof (`value >= threshold`), published as the interval `[threshold, 2^64 - 1]`.
Proof type 1 is a limit proof (`value <= threshold`), published as `[0, threshold]`.
Proof type 2 is a range proof (`lower <= value <= upper`), published as `[lower, upper]` with both bounds free.
Both published bounds MUST lie in the u64 balance domain `[0, 2^64)`, and a verified proof establishes that `note.value` is an integer within the published interval, a subset of `[0, 2^64)` — not merely that some field-arithmetic relation is satisfied.

Normative requirements:

- The verifier MUST compare the public `proofType` against the comparison mode it requested, and MUST reject the proof on any mismatch; a proof valid for one mode is otherwise trivially replayable as a claim for a different mode.
- After exact `proofType`, `context`, state-anchor, and asset-identity binding, the verifier MUST use same-mode monotone interval containment rather than require threshold equality: a proved `>= T` satisfies a `>= R` request only when `T >= R`; a proved `<= T` satisfies a `<= R` request only when `T <= R`; and a proved range `[lo, hi]` satisfies a requested range `[L, H]` only when `lo >= L` and `hi <= H`. Equality is accepted. A different mode remains a `proofType` mismatch and MUST be rejected.
- `context` MUST be non-zero, MUST be a separate co-equal public input never folded into the claim binding (per ADR-0001), and MUST equal a value the verifier itself derived — a caller-supplied context is never authoritative.
- `context` MUST bind the replay-protection context of the authenticated proof request (Safeguard 6), and equals AFP `session_context_field` when carried by `afp:envelope:v1`.
- RECOMMENDED derivation when no session transport supplies a context: `context = H(epoch, chainId, applicationId)`.
- The canonical saturating-interval encoding MUST be used and MUST be enforced by the circuit: proof type 0 requires `upperBound == 2^64 - 1`, proof type 1 requires `thresholdOrLower == 0`, and proof type 2 leaves both bounds free. A statement that does not follow this encoding is non-canonical and MUST be rejected.
- Mode-hiding is deliberately not provided: `proofType` is a public input, and this decision — including its rationale and the alternatives considered and rejected — is recorded in ADR-0007.

Non-normative warning: `context` binding prevents replay of a proof across different verifier/session contexts; it does not prevent reuse of the same proof within one context, since no nullifier is emitted and the note is not consumed.
A static, per-verifier `context` — rather than a fresh value per verification session — degrades replay protection from per-session granularity to per-verifier granularity, and the circuit has no way to detect that this has happened: the non-zero check accepts any fixed non-zero value indefinitely.

### 6.2 Bilateral AFP Reputation History (`zka_reputation`)

The bounded `zka_reputation` prototype supplies the candidate ZKA-family circuit seam for the AFP Introduction Profile §14.6 (AFP.dev, `docs/afp_introduction_profile.md`). It proves an exact count and cumulative value for a clean, finally settled, single-value-domain witness bound to one agreement, one counterparty, an externally supplied history head, and a fresh AFP request context. The subject handle is derived from the prover's private AFP-KDC per-entity seed under an agreement-specific scope; no stable holder commitment, address, proof key, or portable positive score is exposed.

The public `context` is proof-bound, but the circuit itself checks only
`context != 0`; AFP or the verifier MUST derive it from the authenticated
current request and compare it exactly, with stale or repeated counters rejected
externally, to provide freshness and replay protection.

The complete circuit statement and witness definition, identifier encoding, Poseidon2 transcript, known-answer vector, and prototype limitations are normative in [`zka_reputation.md`](zka_reputation.md). That document also records a hard integration boundary: neither AFP nor ZKA yet defines the versioned signed attachment or canonical AFP-atom-to-leaf projection needed to authenticate this circuit's root. Until AFP publishes that adapter contract and cross-language KATs, this prototype MUST NOT authorize an `afp:limit-adjustment:v1` or be described as an operational `afp:reputation-proof`. The circuit cannot authenticate a prover-supplied root or remember a previously accepted counter, and a proof never changes note validity, custody, transfer, withdrawal, collateral, or any other state by itself.

## 7. Bridge Circuits

### 7.1 Ethereum Bridge

Import/export between the ZKA shielded pool and Ethereum. Each Solidity verifier is generated by Barretenberg from the circuit's EVM-target verification key (`bb write_vk -t evm`, then `bb write_solidity_verifier -t evm`) as a per-circuit `*HonkVerifier` contract that implements `IUltraVerifier` (§10.2). Verifier gas is not measured for the `zka_withdrawal` or `zka_root_update` verifiers. The only standalone verifier measurement in this reference implementation is `ZkaPayBatchHonkVerifier.verify()` for `zka_pay_batch` (§3.4), at 2,866,811 gas; it does not apply to other circuits. Export (withdrawal) is unconditional per Safeguard 5.

A conforming ZKA Ethereum bridge contract MUST satisfy the following invariants:

1. **Ownerless and non-upgradeable.** No `owner`, no `pause()`, no `upgradeTo()`, no `setOperator()`, no `setVerifier()`, no `rescue()`, no `migrate()`, no proxy slot, no `selfdestruct`, no constructor `delegatecall`.
2. **Immutable configuration.** Asset address, verifier addresses, operator address (if any), liveness parameters, initial root, and the deployment-binding context MUST be declared `immutable` and set in the constructor.
3. **Append-only mutable state.** Root index, total appended commitments, and last-root-submitted timestamp MUST be strictly monotonic. Consumed nullifiers MUST transition only from `false` to `true`. Accepted roots MUST be removed only by deterministic window pruning.
4. **Root advancement MUST be gated by a root-update proof** verifying that the new root is the correct Poseidon2 incremental fold of the deterministic interleave of on-chain deposit-event commitments and blob-published transfer-announcement commitments into the prior root. The proof system MUST also establish that its private blob-commitment list is the canonical list encoded by the blob identified under invariant 6; the legacy `zka_root_update` circuit (§3.3) does not establish that relation on its own.
5. **Permissionless force-exit path.** When operator silence exceeds a published immutable threshold, any address MUST be able to advance the root and call withdrawal. The contract MUST NOT distinguish operator and non-operator callers for withdrawal.
6. **EIP-4844 blob data availability.** Internal-transfer `NoteAnnouncement`s (§5.7) MUST be carried in EIP-4844 blobs referenced by the same transaction that advances the root. The bridge MUST obtain the blob versioned hash through `BLOBHASH`, bind it to the root-update proof's public inputs, and verify the proof relation required by invariant 4 so the folded leaf list equals the ordered commitment projection decoded from the canonical announcement log. Blob sidecars provide public retrieval only for the network's blob-availability window; a conforming deployment MUST durably archive the canonical payload before expiry, and holders MUST retain the witness data required by §7.1.5. The versioned hash and root-update event alone are not enough to reconstruct expired blob contents.

Historical APL deployment material is outside this public reference specification. The immutable Base APLBridge predates this correction and does not satisfy invariants 4 and 6 because it neither executes `BLOBHASH` nor proves the blob-to-private-leaf relation; it MUST NOT be used as a conforming reference implementation or receive new escrow.

#### 7.1.1 Bridge State (normative)

A conforming bridge MUST hold, on-chain, all state needed for any holder to exit without any off-chain operator service:

| State | Description | Mutability |
|-------|-------------|------------|
| Canonical append log | Note commitments in deterministic settlement order with zero-based leaf indices (§2.4). Carried as contract storage plus `CommitmentAppendEvent`s. | Append-only |
| Accepted root set | Recent Merkle roots per the deployment's accepted-root window (§2.4): latest `N` roots (`N >= 1`), a block-height/epoch/wall-clock window, or both. Window parameters MUST be `immutable` constructor configuration. | Deterministic window pruning only |
| Nullifier set | Consumed nullifiers. | `false → true` only |
| Verifier references | Addresses of the withdrawal verifier and (where root advancement is SNARK-gated, invariant 4) the root-update verifier. | `immutable`, or version-pinned by immutable configuration |
| Escrow balances | Per-asset collateral backing the shielded pool's circulating supply. The bridge MUST maintain `escrow[asset] >= circulatingSupply[asset]` (solvency invariant). | Changed only by deposits and withdrawals |
| Deployment context | The deployment-binding context hash (chain, contract, asset-domain, circuit-domain) that withdrawal proofs MUST bind via their `context` public input. | `immutable` |

No other party — operator, indexer, balance server, prover — holds authoritative state. Anything they hold MUST be reconstructable from the bridge's events (§7.1.3) and MUST NOT be required for exit.

#### 7.1.2 Force-Exit Path (normative)

Force-exit is the ordinary withdrawal, exercised permissionlessly. It is an **unconditional withdrawal path, not an operator-mediated rescue path**: there is no separate rescue circuit, no operator co-signature, no rescue court, and no admin intervention point.

The submitted proof is the standard `zka_withdrawal` proof (§3.2), whose public inputs are `(nullifier, merkleRoot, withdrawalAmount, assetCommitment, externalRecipient, context)`. Per Safeguard 5 (§1.6), no compliance predicate, credential, or binding proof is an input, and the bridge MUST NOT add one.

A conforming bridge MUST process a withdrawal in this order:

1. **Root acceptance.** `merkleRoot` MUST be in the accepted root set; otherwise reject with `UNKNOWN_ROOT` or `STALE_ROOT` (§7.1.4).
2. **Nullifier freshness.** `nullifier` MUST NOT be in the nullifier set; otherwise reject with `NULLIFIER_ALREADY_SPENT`.
3. **Asset support and context binding.** `assetCommitment` MUST identify a configured asset and `context` MUST equal the deployment context; otherwise reject with `UNSUPPORTED_ASSET` / `INVALID_CONTEXT`.
4. **Proof verification.** The proof MUST verify against the immutable withdrawal verifier over exactly the §3.2 public-input vector; otherwise reject with `INVALID_PROOF`.
5. **Escrow sufficiency.** Available escrow for that asset MUST cover `withdrawalAmount`; otherwise reject with `INSUFFICIENT_ESCROW`. (Under the solvency invariant of §7.1.1 this cannot occur absent a bridge defect; the check is defense-in-depth and MUST still be explicit.)
6. **Effects before interactions.** The bridge MUST record the nullifier and decrement supply/escrow accounting **before** transferring funds to `externalRecipient`.

**No challenge period.** For a pure on-chain shielded pool, the accepted root history and the nullifier set are the complete audit surface: a withdrawal is valid iff the proof verifies against an accepted root and the nullifier is fresh. A conforming bridge MUST NOT impose a challenge, delay, or dispute window on shielded-pool exits. Challenge periods exist to police *off-chain* data withholding (state channels, optimistic rollup state) and are out of scope for this path.

**Permissionlessness.** The withdrawal entry point MUST be callable by any address, MUST NOT distinguish operator and non-operator callers, and — together with invariant 5 — MUST remain exercisable when the operator is silent: after the published immutable liveness threshold, any address can advance the root with a root-update proof satisfying invariants 4 and 6 and then withdraw.

#### 7.1.3 Root Publication Model (normative)

Root advancement and commitment-append metadata MUST be observable from settlement-chain execution history. Blob-backed announcement payloads MUST additionally remain retrievable from consensus blob sidecars during the network availability window and from the deployment's durable archive afterward:

- Every appended commitment MUST emit a `CommitmentAppendEvent` (§2.4) carrying the commitment, its leaf index, and the pre/post roots.
- Every accepted root advancement MUST emit a root-update event carrying at minimum `(previousRoot, newRoot, newTotal)` and, for blob-backed SNARK-gated advancement (invariants 4 and 6), the same-transaction blob versioned hash obtained with `BLOBHASH`. Emitting that hash is necessary for reconstruction but does not replace the proof relation between the blob contents and the folded commitments.
- A client or indexer replaying these events together with each referenced canonical blob payload MUST reconstruct the identical tree, leaf order, and accepted root set. The reconstruction source is the consensus blob sidecar while it remains available and the durable archive afterward; holders retain their own exit data per §7.1.5. Indexers and archives remain mirrors, never authorities (§2.4).
- Accepted-root pruning is deterministic window pruning only; pruning MUST NOT be discretionary.

#### 7.1.4 Failure Codes (normative)

Withdrawal rejections MUST be machine-readable (e.g. Solidity custom errors) and distinguish at minimum:

| Code | Condition | Class |
|------|-----------|-------|
| `UNKNOWN_ROOT` | `merkleRoot` never accepted by this bridge | Retryable after re-proving against an accepted root |
| `STALE_ROOT` | `merkleRoot` was accepted but has aged out of the window | Retryable: regenerate the Merkle path against a current accepted root and re-prove |
| `NULLIFIER_ALREADY_SPENT` | `nullifier` already recorded | Terminal for this note |
| `INVALID_PROOF` | Proof fails verification | Retryable after correcting the witness |
| `UNSUPPORTED_ASSET` | `assetCommitment` does not identify an asset configured at deployment | Terminal for this bridge instance |
| `INVALID_CONTEXT` | `context` does not bind this deployment | Retryable with the correct context |
| `INSUFFICIENT_ESCROW` | Escrow for the asset cannot cover `withdrawalAmount` | Retryable; indicates a bridge solvency defect that MUST be observable |

A stale or unknown root MUST NOT invalidate the note: the note remains spendable, and the holder retries with a fresh proof. No failure code, and no party, can transition a note itself to an invalid state — only nullifier consumption by the holder's own proof does that (Safeguard 3).

#### 7.1.5 Client-Retained Witness Data (normative)

Force-exit is only credible if holders can construct the withdrawal witness with **every operator service unavailable**. A conforming client/SDK MUST retain, locally or holder-controlled:

- note plaintext: asset, value, randomness, and any memo needed for spending;
- owner key material or a holder-controlled signer reference (per the §5.7 custody model — never operator-held);
- the note's leaf index, and **either** a cached Merkle path **or** enough append-event data (§7.1.3) to reconstruct one;
- root history references sufficient to select an accepted root;
- note announcement references (§5.7) for re-discovery and audit.

A conforming SDK MUST be able to produce a valid withdrawal proof from this retained data plus public L1 history alone. When witness data is missing, diagnostics MUST be deterministic and machine-readable (missing plaintext, missing/stale path, stale root, spent nullifier), so a holder can distinguish recoverable from unrecoverable states. Retained data MUST NOT expose spending keys to any deployment service.

#### 7.1.6 Relationship to the Aztec Portal Path (informative)

The Aztec native deployment (§8) settles L2 → L1 withdrawals through the Aztec Outbox and an ownerless per-asset portal contract (ADR-0002). That path consumes Aztec kernel-proven L2→L1 messages; it does not use the §3.2 standalone withdrawal proof, this section's bridge state, or the §3.3 root-update circuit. The two exit paths are deliberately separate mechanisms satisfying the same Safeguard 5 obligation; conformance to one does not imply conformance to the other.

### 7.4 Optional external shielded-pool settlement (deployment note)

Distinct from the ZKA bridge circuits above (§7.1), the native ZKA/Pay pool profile (§3.4), and Aztec-native deployment (§8), a conforming deployment MAY delegate settlement to an **external, immutable, operator-free shielded pool** holding a non-freezable asset. ## 8. Aztec Native Deployment

Aztec-native, owner-direct ZKA/Pay is ZKA's strategic flagship deployment profile, subject to [ADR-0010](adr/0010-aztec-flagship-and-production-gates.md). Strategic selection does not enable execution: an exact target must independently pass its integration, capability and deployment gates. Production additionally requires official Aztec resolution of the Alpha V5 proving-system vulnerability, qualification, independent audit and explicit activation. Aztec native is a first-class deployment target for ZKA notes and transfers. ZKA/Coord v2 conformance is separate: an Aztec implementation MUST publish a manifest-bound execution profile and demonstrate the §4 claim with its own conformance evidence; kernel composition alone is insufficient.

The Aztec L1 portal is an Ethereum ingress/egress boundary, not a private bridge: deposit and withdrawal amounts are public on Ethereum, and timing, fees, and receipt metadata remain residual public metadata. Private ZKA transfers occur within the Aztec domain; no cross-domain privacy claim follows from the portal.

### 8.1 ZKA Transfer as Aztec Private Function

```rust
#[private]
fn transfer(
    input_note: ZKANote,
    output_note: ZKANote,
    spending_key: SpendingKey,
    merkle_path: MerklePath
) {
    // ZKA note -> Aztec note stored in Aztec's note hash tree
    // Nullifier managed by Aztec's indexed nullifier tree
    // Kernel circuit handles proof composition
}
```

ZKA notes become Aztec notes. The Aztec-native ZKA/Pay profile uses the §2.3 canonical commitment and canonical asset-id projection, with active values constrained to `1..=u128::MAX`. Every deposit, transfer, withdrawal, popped input value, and change output MUST be range-checked before conversion from `Field` to `u128`; aggregate conservation overflow fails closed. A cross-profile transfer or adapter MUST reject a value that exceeds its destination profile's published maximum before narrowing.

Aztec's note hash tree replaces the protocol-level Merkle tree from §2.4. A v1 Aztec-native ZKA/Pay spend uses Aztec's app-siloed nullifier key and `compute_note_nullifier`; it MUST NOT additionally compute, reveal, or bind the standalone §2.3 `computeNullifier` result. Aztec membership witnesses, note-tree positions, nullifiers, kernel proofs, and verification keys are target-specific. Aztec's indexed nullifier tree provides uniqueness and double-spend prevention for the Aztec target only. Aztec contract code MUST NOT introduce pausable, upgradeable, or administrative paths over note validity (Safeguard 3).

### 8.2 ZKA/Coord via Aztec Kernel Circuits

An Aztec Coord profile MAY represent a step as a private function call and use kernel proof composition. The profile circuit/adapter MUST still emit the canonical Coord v2 receipt, bind the exact Aztec program and artifact identity, enforce the workflow's per-step predicate/topology, and satisfy the same verifier-selected policy and completion checks. Until that profile passes the Coord v2 conformance gate, it MUST be labelled non-conforming experimental. The active Aztec workspace contains no built-in Coord contract: consumers use the canonical SDK verification flow and may delegate an Aztec proof only through an independently registered profile, exact artifact identity, and target-specific verifier implementation. Off-chain proof/VK material is never an Aztec fallback.

### 8.3 Key Mapping

| ZKA Key | Aztec Key |
|---------|-----------|
| `masterSeed` | App-siloed nullifier hiding key `nhk_app` |
| `spendingKey (sk)` | `H("zka/spending", nhk_app)` |
| `viewingKey (vk)` | `H("zka/viewing", spendingKey)` |
| `credentialBindingKey (cbk)` | `H("zkc/credential", nhk_app)` — sibling of `spendingKey` |
| `address` | `H("zka/address", viewingKey)` |

`nhk_app` is the nullifier hiding key that Aztec siloes by contract address, so `sk`, `vk`, `address`, `cbk`, and `holderCommitment` belong to one contract deployment. A new deployment gives the same account new values. Notes and credentials do not carry over, and a holder MUST obtain a new issuer signature for the new deployment. Aztec nullifier keys cannot be rotated, so an Aztec account's privacy secret MUST be generated independently of its signing key. A secret derived from the signing key, which is the Aztec V6 wallet default, MUST NOT be used.

### 8.4 Composable ZKC Compliance

On Aztec, a single transaction can atomically combine a shielded ZKA transfer (§8.1) and an identity binding / predicate proof (§5) via the kernel circuit call stack, without revealing individual claims. Non-revocation is proven in private against the anchor block's nullifier tree, and the compliance-gated transfer checks its recipient in private. §5.8 lists the remaining public outputs of registration, revocation, and the gated transfer.

### 8.5 Cross-Environment Interoperability

Standalone EVM and Aztec-native deployments share only the items their exact manifests declare shared: the BN254/Poseidon2 field and hash parameters, the §2.3 canonical note-commitment formula, the canonical asset-id projection, the `zka/pay/interaction-context/v1` interaction-context profile, and the declared receipt-profile fields. The latter are exactly `interaction-context`, `recipient-output-note-hash`, `contract-instance-address`, and `receipt-profile-version`, with their pinned schema, field encoding, profile version, and domain separator. This declares shared receipt semantics and encodings; it does not claim that every field value is equal across targets. In particular, a contract-instance address is target-specific, and equality of an interaction context or output-note commitment is claimed only when the manifest identifies the same input under the declared semantics. A conforming implementation of the Aztec-native payment-receipt profile MUST carry these fields in a separate recipient-encrypted Aztec private log; `interaction_context` MUST NOT be added to a note field, public state, public log, public function argument, nullifier preimage, or withdrawal input. The receipt-log domain separator MUST be distinct from note-announcement and withdrawal messages. The current synthetic production-forbidden fixture does not establish payment-receipt implementation or production support.

Equal canonical note commitments, asset commitments, or declared receipt fields do not make other settlement state equal. Aztec nullifiers use `aztec-app-siloed-v1`; standalone §2.3 nullifiers, membership witnesses, state-tree positions, proof objects, and verification keys are target-specific. A proof object is target- and VK-bound: an EVM UltraHonk proof is not assumed to verify in an Aztec kernel, or vice versa. A manifest claiming cross-target spend continuity MUST identify an explicit once-only export/import or settlement adapter; equal note hashes alone never authorize independent spending on both targets. An adapter must enforce the destination profile's value bound and reject an out-of-range value before narrowing.

### 8.6 Relationship to Aztec Primitives

ZKA deliberately shares Aztec's cryptographic substrate — BN254, Poseidon2, UltraHonk/Barretenberg, and Noir — so that the Aztec-native deployment **delegates** to Aztec's primitives rather than reimplementing them. This subsection makes the delegation boundary explicit: what ZKA stops carrying on Aztec, and what it continues to add. It is descriptive, not a new normative requirement.

**Delegated to Aztec (native deployment).** In an `aztec.nr` deployment, the host provides the following and ZKA does not carry its own:

| ZKA mechanism (spec) | Provided on Aztec by | Notes |
|----------------------|----------------------|-------|
| Note commitment + Merkle tree (§2.3–§2.4) | Aztec note hash tree | ZKA notes become Aztec notes; the depth-32 Poseidon2 tree is replaced by Aztec's append-only note hash tree |
| Nullifier set (§2.3, §11.5) | Aztec indexed nullifier tree | Non-membership and double-spend prevention are Aztec's |
| Host proof composition | Aztec kernel circuits | Kernel aggregation is usable only inside an explicit Coord v2 profile; it does not itself establish §4 semantics |
| Key hierarchy (§2.2) | Aztec key derivation | app-siloed `nhk_app` is the AFP-KDC seed; `sk` and `cbk` derive as siblings (§8.3) |
| Proof system / field / hash (§2.1, §10) | Aztec native (Honk, BN254, Poseidon2) | Identical by construction under the active compatibility boundary in §2.1 |

On Aztec, the ZKA settlement layer can delegate state primitives to the host. The Coord v2 layer does not reduce to naming conventions: it remains the profile-bound receipt, workflow, policy, and conformance contract defined in §4. ZKA does not claim an improvement over Aztec's host primitives.

**Additive — no Aztec-native equivalent.** The following are ZKA/ZKC contributions that Aztec does not provide and that remain ZKA's own in every deployment, including the Aztec-native one:

1. **ZKC compliance / attestation (§5).** The seed-sibling credential binding (`cbk = H("zkc/credential", seed)`, §2.2), the ZKA-note ↔ ZKC-`holderCommitment` identity-binding circuit (§5.2), selective-disclosure predicates (§5.5, §6), the revocation accumulator and credential lifecycle (§5.6), and the `zka:bundle:v1` compliance envelope (§5.4). Aztec specifies no equivalent compliance-credential system. The Aztec reference contracts implement only part of this set as contract logic over Aztec's app-siloed keys (§5.8): credential issuance authenticated by one pinned issuer key, attribute disclosure, admin revocation, and an account-level compliance registry. They do not verify ZKC issuance (no ZKC proof, issuer registry, or accumulator), and they produce no §5.2 binding proof, so a registration is evidence of that pinned issuer only.
2. **Freedom Safeguards as invariants (§1.6).** Operator-blindness, unconditional exit, no admin/upgrade/pause path over note validity, and verifier accountability. These constrain how Aztec may be *used* rather than duplicating an Aztec feature: §8.1 requires that Aztec contract code introduce no pausable/upgradeable/admin path over note validity (Safeguard 3) — a discipline Aztec's contract model does not impose by default.
3. **Cross-environment compatibility (§8.5).** ZKA pins the note commitment scheme, asset-id encoding (ADR-0003), and domain separators so manifests can identify the exact shared commitment, asset-projection, and receipt semantics across environments that use the shared BN254 field. This is a compatibility contract at the circuit/field/hash level. It does **not** claim equal nullifiers, membership witnesses, state-tree positions, proof objects, or verification keys; nor does it claim that one note simultaneously occupies an Aztec tree and an external bridge tree. Each environment keeps its own state. Cross-target spend continuity requires an explicit once-only export/import or settlement adapter (§8.5); the bridge circuits (§7) are such target-specific settlement mechanisms where applicable.
4. **Settlement-rail independence.** ZKA's note/nullifier/proof model is specified independently of any settlement rail, so the same model runs Aztec-native, against a standalone EVM bridge (§7.1), or with no chain at all on an operator-run platform. Aztec's primitives are inseparable from the Aztec rollup; ZKA's are not bound to any one host.

**Scope summary.** On Aztec specifically, ZKA's value is the additive set above — ZKC compliance, the Freedom Safeguards, and cross-environment note compatibility — layered on delegated Aztec machinery. ZKA's rail-independent primitives (its own tree, nullifier set, recursion plumbing, and the standalone verifier path) are justified by the non-Aztec deployments, not by the Aztec one. Aztec is the strategic flagship deployment profile under the gates stated in ADR-0010; that status does not make it production-certified. This subsection records the boundary between delegation and addition explicitly.

## 10. Proof Format

### 10.1 UltraHonk Proof (Barretenberg)

```typescript
interface UltraHonkProof {
  proof: Uint8Array;           // Serialised UltraHonk proof bytes
  publicInputs: Field[];       // BN254 scalar field elements
  verificationKey: Uint8Array; // Serialised verification key
}
```

Proofs are generated by Barretenberg (`bb prove`) or NoirJS (`noir_js` + WASM). Verification is performed on-chain by the circuit's generated `*HonkVerifier` Solidity contract (§10.2), against a proof produced for the EVM target (`-t evm`).

### 10.2 Solidity Verifier Interface

```solidity
interface IUltraVerifier {
  function verify(
    bytes calldata _proof,
    bytes32[] calldata _publicInputs
  ) external view returns (bool);
}
```

The verifier is generated per circuit by Barretenberg: `bb write_vk -t evm` writes the EVM-target verification key, and `bb write_solidity_verifier -t evm` generates the contract from that key. The generated `HonkVerifier` contract is renamed to a circuit-specific name, for example `ZkaTransferHonkVerifier`. Each circuit has its own deployed verifier instance that implements `IUltraVerifier`. Verifier contracts MUST be non-upgradeable and admin-free (Safeguard 3).

## 11. Security Considerations

### 11.1 Cryptographic Assumptions

| Assumption | Implication if Broken |
|------------|----------------------|
| Discrete log (BN254) | Spending key recovery |
| Poseidon2 collision resistance (BN254 field) | Note forgery / identity binding forgery |
| UltraHonk soundness (Barretenberg) | Invalid proofs accepted |
| Noir ACIR compilation correctness | Circuit constraints deviate from spec |
| Accumulator security | Revoked credentials appear valid |
| Master seed secrecy | Full compromise of both ZKA and ZKC identities |

### 11.2 Implementation Requirements

| Requirement | Rationale |
|-------------|-----------|
| Constant-time nullifier queries | Prevent timing attacks |
| Secure randomness for note creation | Prevent commitment grinding |
| Atomic nullifier recording | Prevent double-spend race conditions |
| Merkle root recency checks | Prevent stale state attacks |
| Pinned Noir + Barretenberg versions | Prevent breaking changes in proof format |
| No admin/pausable/upgrade paths over notes | Enforce Safeguard 3 |
| Unconditional unshield/withdraw | Enforce Safeguard 5 |

### 11.3 Privacy Limitations

| Limitation | Mitigation |
|------------|------------|
| Timing correlation | Randomized delays, batching |
| Transaction graph (long-term) | Dummy transactions |
| Note value distribution | Standardized denominations |
| Metadata leakage | Encrypted memos |
| Cross-chain correlation | Bridge batching, timing randomization |
| Disclosure accumulation over time | Minimal disclosure default (Safeguard 2), per-session fresh binding |

### 11.4 Bridge Security

| Risk | Mitigation |
|------|------------|
| Bridge contract compromise | Ownerless, non-upgradeable contract with immutable configuration and append-only state (§7.1 invariants 1–3); no admin, governance, or multi-sig key over bridge liquidity or note validity |
| Cross-chain replay | Chain-specific context binding |
| Asset mismatch | Strict asset ID verification |
| Aztec kernel upgrade | Version-pinned circuit IDs |

### 11.5 Nullifier Storage Requirements

Nullifier storage MUST provide atomic append with at-least-once delivery guarantees. Event-sourced stores (e.g. KurrentDB/EventStoreDB) satisfy this; the nullifier event log doubles as a compliance audit trail. In Aztec native deployments, Aztec's indexed nullifier tree provides these guarantees natively.

### 11.6 Post-Quantum Considerations (Draft)

BN254 discrete-log and the UltraHonk proving system are not post-quantum secure. A future revision will specify a PQ migration path (hash-based commitments are Poseidon2 and remain conjecturally PQ-resistant for collision; key derivation and proof system are the migration surface). This remains open work for a future revision.

## 12. Conformance

### 12.1 ZKA Conformance Levels

| Level | Requirements |
|-------|--------------|
| **ZKA-Core** | Transfer proofs, nullifier tracking, canonical Merkle append/root handling, note discovery, non-custodial key ownership, Safeguards 3 & 5 |
| **ZKA-Coord** | Core + Coord v2 profile-bound receipt, recursive DAG proof, verifier policy, and completed conformance gate (§4) |
| **ZKA-Full** | Coord + viewing keys + selective disclosure |
| **ZKA-Compliant** | Full + ZKC integration (§5), all six Safeguards |
| **ZKA-Aztec** | Full Aztec native deployment plus an independently conforming manifest-bound Coord v2 Aztec profile and the value, nullifier, and interoperability boundaries of §§2.3, 8.1, and 8.5 |

The Safeguards named in this table are what each level adds; they do not narrow the scope that §1.6 sets. Safeguards 3 and 5 bind every level. Safeguards 1, 2, and 4 bind any ZKC predicate or bundle used with ZKA, at any level. Safeguard 6 binds every disclosure request that a verifier makes, at any level. `ZKA-Compliant` is the level at which the ZKC integration itself is required.

The **ZKA-Coord** level requires the exact soundness claim and evidence gate of §4. The reference profile is bounded to fan-in 4, depth 32, and 4096 unrolled proof nodes; no target may claim unbounded depth or infer conformance from host proof composition alone. Another proving mechanism can conform only through an explicit manifest-bound profile with equivalent receipt, workflow, policy, data-flow, completion, and adversarial-verification evidence.

**Bridge-deploying conformance.** Any conformance level claimed by a deployment that operates a ZKA Ethereum bridge MUST additionally deploy a root-update verifier referenced by the bridge contract as `VERIFIER_ROOTUPDATE`, whose proof system satisfies invariants 4 and 6 of §7.1, and the bridge MUST satisfy all six invariants of §7.1. The legacy `zka_root_update` circuit (§3.3) alone does not establish the blob-to-leaf relation that invariant 4 requires, so a verifier for that circuit alone does not satisfy this clause.

**Aztec conformance.** A `ZKA-Aztec` deployment MUST publish a manifest that declares `nullifier_semantics = aztec-app-siloed-v1` and the selected value width and maximum (`u128` and `u128::MAX` for the Aztec-native ZKA/Pay profile). The manifest MUST state that nullifier, witness, proof, and verification-key equality with EVM is not claimed; it MUST enumerate any shared commitment, asset-projection, and receipt fields by exact encoding and domain. It MUST identify an explicit adapter when claiming cross-target spend continuity.

### 12.2 ZKC Integration Conformance Levels

ZKC conformance levels are owned by the **ZKC Specification v0.4 §9.1**. The core ladder is strictly monotonic — `ZKC-Core` → `ZKC-Standard` → `ZKC-Full` (Full is the highest core level) — and `ZKC-Agent` is an orthogonal extension profile, **not** a level above `ZKC-Full`. `ZKC-Core` includes KYC proofs, the credential rebind circuit (`zkc:proof:credential_rebind:v1`), and basic verification. This spec does **not** re-declare a parallel `Integration-*` taxonomy; a deployment integrating ZKC MUST conform to the ZKC v0.4 §9.1 level it claims, and tooling MUST treat the level name as ZKC-namespaced rather than inferring rank from the ZKA taxonomy. The ZKA-side requirements that gate the `ZKA-Compliant` level (§12.1) are: shared key hierarchy (§2.2), identity binding circuit (§5.2), compliance bundle envelope (§5.4), and all six Freedom Safeguards (§1.6).

A deployment claiming `ZKA-Compliant` MUST satisfy all six Freedom Safeguards (§1.6). Below that level, the Safeguards still bind as §1.6 scopes them (§12.1): Safeguards 3 and 5 at every level, Safeguards 1, 2, and 4 wherever a ZKC predicate or bundle is used with ZKA, and Safeguard 6 wherever a verifier requests a disclosure.

## Appendix C: ZKA-ZKC Integration

### C.1 Current ZKC v0.4 relationship

ZKC Specification **v0.4** is the current ZKC integration target. It retains linkable `zkc:proof:v1` and adds `zkc:proof:v2` with anonymous and scoped presentation profiles. ZKA uses the same `cbk = H("zkc/credential", masterSeed)`, scoped domain separator, anonymous zero sentinel, Poseidon2/BN254 field encoding, registry-selected predicate identifiers, replay context, issuance, and revocation rules. Predicate versions are independent of the carrying envelope version: notably, `zkc:proof:selective_disclosure:v1` is carried in a v2 anonymous or scoped envelope. ZKA adds only the note-ownership conjunction in `zka_transfer_binding_v2`; it does not redefine ZKC predicate verification.

ZKA-side reconciliation: `zka:bundle:v1` wraps both ZKC envelope families and dispatches verification by the exact `(envelopeVersion, presentationProfile, proofType)` tuple. Payment bindings accept v1/linkable or v2/scoped only; payment-free work attestations may carry v2/anonymous because identity remains bound to the authenticated session-context field projection. The legacy v1 circuit and wire shape remain accepted unchanged.

**Precedence:** Per ZKC v0.4 §1.4, where ZKC and ZKA §1.6 differ in wording on a Freedom Safeguard, the safeguard *intent as stated in ZKA §1.6 governs*. ZKA §1.6 is the authoritative source for safeguard intent; ZKC mirrors it.

**Required ZKC properties:**

1. **Non-exclusive proof types (§5.5).** ZKC's well-known identifiers and reference schemas MUST NOT privilege or require one type or provider.
2. **Open-source predicates (Safeguard 4).** Predicate circuits MUST be auditable and versioned, with default refusal of opaque predicates.
3. **Conformance hierarchy.** The ladder is `ZKC-Core` → `ZKC-Standard` → `ZKC-Full`; `ZKC-Agent` is an orthogonal extension profile.

**Notation reference.** Both specifications reference AFP-KDC for hashing, domain separation, and seed-to-key derivation rather than a ZKA-versioned derivation. AFP-KDC v1.0.2 §A.3 defines the deployed Blake2b-512 little-endian field-tag derivation. The derivation facts cited above (`cbk = H("zkc/credential", masterSeed)`, `H("zkc/binding", cbk)`, Poseidon2/BN254) are defined by AFP-KDC §A.6 and are cited here, not redefined.

**Credential rebind reference.** ZKC v0.4 §4.5 defines `zkc:proof:credential_rebind:v1` as a ZKC-Core circuit that proves holder-controlled migration from `oldHolderCommitment` to `newHolderCommitment` without revealing either seed, either `cbk`, any ZKA address, any spending key, or payment activity. ZKA does not duplicate that circuit. ZKA's obligations are to keep note migration private via self-transfer batching (§5.7), keep any issuer-retained old-to-new holder-commitment mappings sealed and minimized (§5.7), and ensure rebind proofs never affect ZKA note validity, custody, transferability, withdrawal, nullifier semantics, or revocation semantics.
